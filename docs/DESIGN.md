# Tagalot — Design Document

Status: draft v1 · Owner: project author · Implementation: Python (Rust reserved for isolated hot spots)

## 1. Overview

Tagalot is a desktop, tag-based file browser. Work is organized into **keeps**: self-contained projects that each have their own database, tag tree, list of watched directories ("roots"), and a **theme** that defines what kind of content the keep manages (music, 2D art assets, movies, …).

Tagalot never stores or moves user data. A keep holds only metadata and caches; the files themselves stay where they are, commonly on network shares (SMB/UNC paths, mapped drives, NAS mounts). This is why Tagalot is a native desktop app rather than a web app.

### Goals

- Browse and filter tens of thousands of items per keep with fast, hierarchical tag filtering (include and exclude).
- Make tagging fast: a filterable tag panel with drag-and-drop and keyboard application to one or many items.
- Plug-and-play themes: a programmer can add a new content type (entity classes, metadata fields, views, thumbnail logic, actions) by dropping a single Python file into a themes folder, without changing the application.
- Work well with network shares, including shares that are slow or temporarily offline.
- Never modify, move, rename, or delete the user's files. The one exception is writing metadata back into a file, only in a folder the user marked writable and only by an explicit action (§4 *Writing back to files*).

### Non-goals (v1)

- Multi-user concurrent editing of one keep.
- Writing metadata back into files in general (for example, editing ID3 tags). The narrow exception is planned for Markdown front matter (§4 *Writing back to files*, M20).
- Playing media or rendering fonts inside the app; files are handed to the OS or a configured program.
- Online metadata scraping (the theme API should leave room for it; see §14).

## 2. Glossary

| Term | Meaning |
|---|---|
| **Keep** | A folder containing one keep's config, database, and caches. Uses exactly one theme. |
| **Root** | A directory the keep watches. A keep has one or more roots. |
| **Resource** | A file or directory found under a root. Identified by root id + relative path. |
| **Entity** | A thing the user browses and tags (a Song, Album, Artist, Movie, Font…). Defined by the theme. May map to zero, one, or many resources. |
| **Role** | The function a resource plays for an entity ("audio", "cover", "photo", "screenshot", "folder"). |
| **Containment** | A parent/child relationship between entities (Artist ⊃ Album ⊃ Song), used for tag inheritance, "show contained items", breadcrumbs, and drill-down. |
| **Tag** | A node in the keep's hierarchical tag tree. Tags attach to entities. |
| **Theme** | A Python module that defines entity types, fields, roles, containment, ingestion, thumbnails, views, and actions. |
| **View** | A theme-declared screen: a search preset or an entity detail page. |

## 3. Technology choices

- **Python 3.12+**, managed with **uv**.
- **PySide6 (Qt 6)** for the UI. Qt's model/view classes render only visible rows, which keeps 50k-item lists responsive, and Qt provides drag-and-drop, docking, and `QDesktopServices` for opening files.
- **SQLite** (one database per keep) via **SQLAlchemy 2.0**: declarative ORM models (`Mapped`, `mapped_column`, `select()`) for core tables, and Core `Table` objects built at keep open for theme tables (§9). SQLModel was rejected because it fits neither the joined-table entity layout nor per-keep dynamic tables. Requires SQLite **3.45+ with FTS5** (for the trigram tokenizer's `remove_diacritics` option, §8); the app checks this at startup, before opening any window, by creating a trigram FTS5 table in an in-memory database (FTS5 can be compiled out of an otherwise recent SQLite), and shows a dialog explaining how to fix it if the check fails.
- **Pillow** for image decoding and thumbnails (including the PSD composite image).
- **mutagen** for audio metadata and embedded cover art.
- **pymediainfo** (MIT; #259) for video details in the movies theme: runtime, picture size, codecs, and audio languages for MKV, MP4, AVI, and the rest. Its wheels bundle the MediaInfo library for Windows, macOS (Intel and Apple silicon), and Linux (glibc 2.27+), so nothing else is installed; it reads headers, not frames. Chosen over pure-Python readers (more formats, one code path) and ffmpeg (a 20–30 MB binary whose output would be parsed as text).
- **Archives:** `zipfile` (stdlib), `py7zr` for 7z, `rarfile` for RAR (requires an external `unrar`/`bsdtar`; RAR support degrades gracefully when missing). All behind one internal `ArchiveReader` interface.
- **For the books theme** (M20, #297): **pypdfium2** (Apache-2.0/BSD; PDF metadata and first-page covers; PyMuPDF was passed over for its AGPL license; its wheels bundle PDFium for each platform; not thread-safe, so every call holds one lock, `themes.readers.PDFIUM`) and **PyYAML** (MIT; YAML front matter in Markdown, read with `safe_load`; TOML front matter uses `tomllib`). Both are imported only when a PDF or YAML front matter is read.
- **ruamel.yaml** (MIT; #299, chosen in review): editing YAML front matter round-trip for **Write to file…**, so comments, quoting, key order, and list style stay. PyYAML can't keep comments; rewriting the whole block was passed over for that reason. TOML front matter is edited by replacing only the lines of the keys written (no round-trip TOML library).
- **platformdirs** for per-user config/cache paths; **tomllib** / **tomli-w** for TOML.
- **hashlib.blake2b** (stdlib) for fingerprints.
- Tooling: **pytest**, **pytest-qt**, **ruff** (lint and format), **mypy**.

A windowed Windows build has no console, so `--output FILE` writes either to a file.

Each folder build carries a `README.txt` saying so, and so do the release notes. ### Why Python, not Rust

The expected bottlenecks are directory scanning over network shares and thumbnail generation. Both are I/O-bound, so a faster language would not help much; running them in background workers does. Python also makes the plugin requirement straightforward: themes are importable modules. Rust has no stable ABI for dynamically loaded plugins, which would make drop-in themes much harder. If profiling identifies a CPU-bound hot spot (hashing, walking, image decoding), that function can be moved to Rust via PyO3 behind the same Python interface.

### Performance (measured, #131)

`scripts/profile_scan.py PATH --theme T [--cprofile]` makes a throwaway keep in `scratch/profile/`, scans PATH, times each phase from the scan's progress messages, rescans, and times thumbnails from a cold cache on 1 and N threads. Measured in October 2026 on Windows 11, on a folder of 9,341 files (9,226 JPEGs, about 10 GB) on an SMB share, and on a local copy of it:

| | Share | Local |
|---|---|---|
| First scan, generic theme | 98 s (fingerprinting 80 s) | |
| First scan, assets2d | 296 s | 135 s |
| Walking | 0.5 s | 0.1 s |
| Fingerprinting | 79 s | 30 s |
| Reading (the theme's `prepare`: image size and picture hash) | 164 s | 53 s |
| Ingesting (the DB writer) | 52 s | 52 s |
| Rescan, nothing changed | 0.8 s | 0.2 s |
| Thumbnails, 1 thread / 8 threads | 6.3 / 42 per s | 6.8 / 47 per s |

Where the time goes (cProfile):

- **Opening and reading files** dominate on the share: `open()` alone is 115 s of the assets2d scan (6 ms each; 28 s locally, where antivirus on open is most of it), and `read()` 56 s. Hashing itself (blake2b) is 1 s. This is latency, not CPU, and it is spent one file at a time: fingerprinting and `prepare` each read files sequentially.
- **Image decoding** (Pillow, in C, already decoding JPEGs at 1/8 size) is 43 s, the same on both. Pillow releases the GIL while decoding, so threads help.
- **Ingest** is CPU in SQLAlchemy: about 18 statements per item (169k for 9.4k items), with statement compilation and caching around 27 s of the 52 s. It is the same on the share and locally.
- **Thumbnails** scale almost linearly with threads (7× on 8 threads), since each is I/O plus GIL-free decoding.
- Walking and rescans are already fast.

**Conclusion: no Rust.** None of the costs is Python code a faster language would remove: they are I/O latency (fixed by doing several files at once), C code that is already native (decoding, hashing), and the number of database statements per item (fixed by batching them). Follow-ups: fingerprint files on several threads (#273, done: below), run the theme's `prepare` on several threads (#274, done: below), resolve background thumbnails on several threads (#275, done: below), and fewer, batched statements in ingest (#276, done: below).

**Parallel fingerprints** (#273), on the same share with the generic theme: fingerprinting took 77 s hashing one file at a time and 15.5 s hashing 8 at once (the first scan went from 95 s to 34 s; runs alternated 8, 1, 8 to rule out caching). 16 threads gave 13 s and 32 gave 12 s, so 8 is kept, which is also gentler on a single spinning disk. On the local copy, with warm caches, it was 1.7 s against 0.85 s. `scripts/profile_scan.py --fingerprint-threads N` repeats the comparison.

**Parallel reading** (#274), the same share with assets2d. Phases are now the time the scan *waited* for each, since reading the next batch overlaps ingesting this one:

| | First scan | Waiting on reading | Waiting on ingest |
|---|---|---|---|
| Before #273 | 296 s | 164 s | 52 s |
| Parallel fingerprints, one reader | 192 s | 145 s | 31 s |
| 8 readers (now) | 107 s | 54 s | 37 s |
| 16 readers | 104 s | 51 s | 37 s |

8 readers are kept. Beyond them, the rest is CPU in one process: Pillow's decoding and ingest's Python share the GIL. A process pool could go further, but would need themes to be picklable and their `prepare` results to cross processes, which is not worth it until #276 makes ingest cheaper. `--prepare-threads N` repeats the comparison.

**Background thumbnails** (#275), 300 pictures from the same share by the queue, from a cold cache: 53.8 s on one thread (5.6 a second), 13.4 s on 4 (22.4), 7.3 s on 8 (41.3). 4 threads are kept, since the grids have 4 of their own for what is on screen and both read the same share; `--threads 1 4 8` repeats the comparison.

**Cheaper ingest** (#276). A new file cost 14.1 statements with the generic theme and 18.8 with assets2d, most of them lookups that can't find anything for an item made in the same transaction, each statement built afresh by SQLAlchemy. Now 6.2 and 6.6:

- The ingest session remembers what it learned, which stays true because only it writes while its transaction is open: the next entity id (looked up once), keys looked up or made, the items it made (no user edits, hand-made links, or thumbnail yet, so those lookups are skipped), each item's user-edited fields, the values it already wrote (the same artist title for every image isn't written again), and whether the keep has any merged items at all (most never do; merging never happens during an ingest).
- New items' depth-0 closure rows are added together at flush.
- The statements every item runs (the key lookup, the entity and theme-row inserts, the link, the provenance upsert, whose-file-is-it) are built once with bound parameters, on Core tables rather than through the ORM.

Ingesting 50,000 generic files went from 122 s to 13 s (`tests/core/test_ingest_cost.py`, with a test of statements per file that runs every time). On the share, the generic theme's ingest went from 17.4 s to 2.7 s and its first scan is now 18.8 s (98 s when profiling began); assets2d's ingest wait fell from 37 s to 4.7 s, leaving its first scan (102 s) almost all image decoding in `prepare`. That is where a process pool would now pay off.

## 4. The keep on disk

```
MyMusic.keep/
  keep.toml        # identity, theme, roots (shared, portable)
  keep.db          # SQLite: resources, entities, tags, theme tables
  thumbs.db        # SQLite: thumbnail blobs (disposable cache)
  fulltext.db      # SQLite: documents' text, when searching inside them (§8)
  ui_state.json    # view toggles, column widths, saved layout (optional)
```

### keep.toml

```toml
[keep]
id = "0b6e3c1e-6f0a-4b54-9a8e-2b2d7f1c9d41"   # UUID, never changes
name = "Music"
format_version = 15                         # core schema version

[theme]
id = "music"
version = 1                                 # theme schema version

[[roots]]
id = "nas-music"                            # stable, referenced by resources
name = "NAS music share"
path = '\\nas\music'
exclude = [                                # new roots start with DEFAULT_EXCLUDES
    '**/.DS_Store',
    '**/._*',
    '**/Thumbs.db',
    '**/@eaDir/**',
    # …
]

[thumbnails]                               # optional
max_size = 512                             # overrides the theme's thumbnail_max
after_scan = false                         # don't make a scan's thumbnails in the background

[online]                                   # once the user answered (§9 Online details)
lookups = "allow"                          # or "never"; absent: not asked yet, nothing looked up

[contents]                                 # searching inside documents (§8)
index = "words"                            # or "substrings"; absent: Off, nothing read

[notes]                                    # notes (§9 Notes); absent: no notes folder
root = "nas-music"                         # the notes folder: a root id
path = "Notes"                             # and the folder inside it ("" for the whole root)
writable = true                            # Save as note… may write there (asked first)
new_notes = "folders"                      # or "one-folder" (typed by tagalot-type)
ignore_keys = ["mood-board"]               # front-matter keys never made Extra fields
```

### Rules

- **Resources store root id + relative POSIX-style path**, never absolute paths. Changing a root's path (new drive letter, new server) requires editing one value.
- **Per-machine root overrides.** The per-user settings file (see below) can map `(keep id, root id) → local path`, so the same keep opened on two machines can reach a share through different mount points.
- **Offline is not deleted.** If a root is unreachable at scan time, its resources are marked offline and nothing is removed. Resources are only marked missing when their root is reachable and the file is gone. Files the scan now leaves out (a new exclude pattern, an extension the theme no longer takes) are flagged *skipped*, not missing (§6).
- **Not watched.** A root with `watched = false` stays in `keep.toml` but isn't scanned; its resources are marked offline, and its items keep their tags. Watching it again (or adding the same folder) and scanning reconnects them. Only removing a root *with its items*, an explicit choice in the Keep configuration window (§12), deletes anything: the root's resources, the items with files only there, and containers left empty. Files on disk are never touched.
- **Keep location.** `keep.db` should live on a local disk. SQLite locking over SMB is unreliable. The app warns (but does not refuse) when a keep is opened from a network path, and a keep is single-user in v1. Detection is best effort and never blocks opening: on Windows, UNC paths and drives that `GetDriveTypeW` reports as remote (mapped drives); on Linux and macOS, the mount's file-system type (nfs, cifs/smbfs, afpfs, sshfs, and similar; WSL's `/mnt/c` counts as local).
- **Keeps and roots never contain each other.** Creating a keep inside one of its roots, or with a root inside the keep folder, is refused: the scanner would index the keep's own files.
- **Creating a keep** requires a new or empty folder and writes `keep.toml` with a fresh UUID; the databases are created on first open.
- SQLite runs in **WAL mode** with a `busy_timeout` for local keeps. Keeps on a network path use the rollback journal (`journal_mode=DELETE`, `synchronous=FULL`) instead, because WAL needs shared memory on one host and does not work over network file systems. Every connection turns foreign keys on. Connections for UI queries set `query_only`, so only the DB writer can write, and are not pooled: each closes when its query is done, so a query still running in a worker when the keep closes can't leave the file open (and, on Windows, locked). SQLAlchemy, not Python's `sqlite3` module, issues `BEGIN`, so DDL is transactional and a failed migration rolls back cleanly.
- **keep.toml is hand-editable.** Tagalot writes strings as TOML literal strings (`'\\nas\music'`) so paths need no escaping, falling back to escaped basic strings only when a value contains `'` or a control character. Root paths are kept exactly as written (a string, not a parsed path), because a keep written on Windows may be read on another OS. Writes are atomic (temp file, then replace).
- **Notes on Skip entries** (#334). A root's `exclude` patterns may each have a note saying why it is there, in a sub-table after the root's keys: `[roots.exclude_notes]` with `'pattern' = 'note'` lines. `exclude` itself stays a plain list of strings, so an older build still reads the keep (it ignores the unknown key, with a warning) and a hand edit stays simple. A note for a pattern no longer in `exclude` is dropped when the file is written. Tagalot writes notes when it skips a file itself: an export saved inside a watched folder ("Saved here by Export BibTeX… on 2026-10-05; skipped so the keep doesn't read its own export back") and Triage's **Skip** ("Skipped from Triage on 2026-10-05"). The user writes and edits them in Keep configuration's Skip box, after the pattern: `Exports/papers.bib # why`. So that ` # ` always starts a note, `core.triage.exact_pattern` brackets a `#` in a file name (`[#]`, still matching it). Themes don't add Skip entries; letting a theme ignore files with a reason was left out (no theme needs it yet).
- **Default excludes.** New roots start with `core.keep.DEFAULT_EXCLUDES`, operating-system and NAS leftovers that are never user content: macOS `.DS_Store`, AppleDouble `._*` companions (which carry the real file's extension, so they would otherwise look like photos), `.AppleDouble`, `.Spotlight-V100`, `.Trashes`, `.fseventsd`, `.TemporaryItems`; Windows `Thumbs.db`, `desktop.ini`, `$RECYCLE.BIN`, `System Volume Information`; Synology `@eaDir` and `#recycle`. They are written into `keep.toml` rather than applied implicitly, so they are visible and can be edited or removed. Other dot files are left alone. Existing keeps are not changed. Lists too long for one line are written one item per line.
- **Theme options** (#82). `[theme.options]` sets the theme's declared options (§9) for the keep (`artist_level = 2`), and a root's `options = { artist_level = 1 }` overrides them for that root. Values are numbers, true/false, or strings; names and types are checked against the theme when a root is scanned, and a value that doesn't fit is reported and replaced by the option's default. They are set in the Keep configuration window (§12), or by hand.
- **Thumbnail size.** The optional `[thumbnails] max_size` overrides the theme's `thumbnail_max` (§10) for this keep: the resolution thumbnails are made and cached at. It is set in the Keep configuration window's Thumbnails tab (§12), which applies it at once, or by hand.
- **Writing back to files** (M20, #299; `core/writeback.py`, `ui/write_back_dialog.py`). The one exception to "never modify the user's files", and narrow on purpose:
  - **Off unless a folder allows it:** a watched folder is marked writable in Keep configuration (Folders → **Write back**, which asks first; `writable = true` on the root in `keep.toml`), off by default. No other root is ever written to; the folder is checked again just before writing.
  - **Only an explicit action writes**, never a scan, a tag change, or anything automatic: **Write to file…** on the selected items (their right-click menu, or More on an item's page), offered for the theme's `write_back` types (the books theme: Book). It writes the Markdown files (`.md`, `.markdown`) of the items' primary role. It isn't an Edit → Undo step: the backups are the way back.
  - **Before writing:** the files are read in a worker and a preview shows each one's front matter before and after (as a diff), with a box to leave it out, and why a file won't be written (its folder doesn't allow it, it changed since Tagalot read it, it isn't UTF-8, its front matter doesn't parse) and which items have no Markdown file. The file must be as Tagalot last read it (size and modification time) when planned and again when written, else it is skipped and reported. A copy goes to the keep folder (`backups/<date-time>/<root id>/<path>`), not beside the file; the new content is written beside the file under a temporary name and renamed over it. Afterwards the files' roots are scanned, so Tagalot reads what it wrote; writing again then finds nothing to change.
  - **Only the metadata block changes** (the front matter between its markers); the rest of the file is kept byte for byte, line endings included. YAML is edited round-trip (ruamel.yaml, chosen in review): comments, quotes, key order, and a list's style (`[a, b]` or one per line) stay. TOML has only the lines of the keys written replaced (a list inline). A key is matched ignoring case. A file without front matter gains a YAML block at the top.
  - **What is written** (chosen in review): the item's **tags**, and the **fields the user edited** in Tagalot (provenance `user`); values that came from the file are already there. Tags go under the file's `tags` key (else its `keywords`, else a new `tags`): each tag list keeps the file's own words, less a word whose tag the user took off the item (a file-tag removal, §7); then the item's other tags (by hand, or from its other files) as full paths (`Genre/Fantasy`, as Obsidian writes nested tags). A word that matches no tag stays.
  - **The theme API** (version 3, chosen in review): `Theme.write_back` names the types whose Markdown files may be written, and `Theme.front_matter(entity_type, item, edited, current)` maps the edited fields to front-matter keys (`{key: value}`, `None` removing one), seeing the file's current keys so it can keep their names. The core does all reading and writing; themes never open a file for writing.
- **Saving an export** (#322, decided in review). An action's `save_text` lets the user save a file where they choose, which may be inside a watched folder: a narrow second exception to "never modify the user's files", since the user picks the place. Inside a watched folder, Tagalot first warns that it will leave the file out of scans, then adds an exact pattern for it to that folder's Skip list (`exclude` in `keep.toml`, shown in Keep configuration) before writing it, so the keep never reads its own export back (a research keep would otherwise take an exported bibliography as a source of its papers' details). It never replaces an existing file in a watched folder; choose a new name. Elsewhere, the save dialog's own "replace?" applies. The Skip entry carries a note saying so (#334, *Notes on Skip entries* below).
- **Unknown keys in keep.toml are ignored with a logged warning**, so an older build can still open a keep written by a newer one. They are not preserved when Tagalot rewrites the file.

### Per-user settings (not in the keep)

Stored in `platformdirs.user_config_dir("tagalot", appauthor=False)/settings.toml` (on Windows `%LOCALAPPDATA%\tagalot\settings.toml`; deliberately not a roaming location, since the contents are machine-specific):

- Recent keeps: keep folders, most recent first, at most 10, compared case-insensitively on Windows.
- Per-machine root path overrides: `[root_overrides.<keep id>]` tables mapping root id → local path.
- File-handler overrides (§11), because application paths differ by machine: `[[handlers]]` tables with `ext`, optional `role`, and `command`. A rule for an extension and role wins over one for the extension alone. Commands may only use the `{path}`, `{dir}`, and `{name}` placeholders.
- Extra theme search directories (`theme_dirs`).
- Front-matter keys the user never wants as Extra fields, in any keep (`[notes] ignore_keys`, §9 *Notes*).
- The folder last chosen in any of Tagalot's folder pickers (`last_folder`): every picker starts there (`ui/folder_picker.py`), and a new keep's location is filled in with it. Opening a keep folder remembers the folder holding it. Until something is chosen, pickers start at the home folder.

Settings never block startup: a missing file means defaults; a file that cannot be parsed is renamed to `settings.toml.invalid` and defaults are used; individual invalid entries are skipped. Every problem is logged.

## 5. Data model

All core tables are created and owned by the core. Theme tables are prefixed with the theme id (`music_song`, `movies_actor`).

Conventions for core tables:

- **Timestamps** are stored in UTC and read back as timezone-aware datetimes; naive datetimes are rejected.
- **Enumerated columns** (`resource.kind`, `resource.status`, `field_provenance.source`) are stored as text with a CHECK constraint on the allowed values.
- **Deletes:** link rows (`entity_resource`, `entity_contains`, `entity_ancestor`, `entity_tag`, `field_provenance`, `tag_alias`) cascade with the entity, resource, or tag they link. Deleting a resource clears any `entity.thumb_resource_id` that pointed at it. Deleting a tag that has children, or a root that still has resources, is refused by the database; the tag delete operation (§7) and root removal handle those explicitly. Deleting an entity never deletes a resource.

### Core tables

**root** — mirrors keep.toml for joins and status.
`id (text pk)`, `name`, `online (bool)`, `last_scan_at`, `last_error`.

**resource** — a file or directory under a root.
`id (int pk)`, `root_id`, `relpath` (POSIX), `kind` (`file`/`dir`), `ext` (lowercase), `size`, `mtime_ns` (integer nanoseconds, compared exactly when diffing), `fingerprint` (nullable), `status` (`ok`/`offline`/`missing`), `skipped` (bool: scans now leave it out, §6; core format 5), `first_seen_at`, `last_seen_at`, `parent_resource_id` (nullable; reserved for archive members, §14).
Unique `(root_id, relpath)`. Index on `fingerprint`.

**entity** — base table for every theme entity (joined-table layout: each theme type's table shares its `id`).
`id (int pk)`, `type` (namespaced discriminator such as `music.song`), `title` (display name, denormalized for fast listing and sorting), `ingest_key` (nullable text; the theme's stable natural key for the entity, §9), `extra` (JSON, user-defined fields), `created_at`, `updated_at`, `thumb_resource_id` (nullable; memoized thumbnail source).
Unique `(type, ingest_key)`. The key lets re-ingest find an existing entity even after the user renames its title.

**entity_resource** — role-based links.
`entity_id`, `resource_id`, `role`, `sort_order`, `by_user` (made by hand, core format 6, #243; §9 ingest context).
PK `(entity_id, resource_id, role)`. Index on `resource_id`.

**entity_contains** — containment edges declared by the theme's ingester.
`parent_id`, `child_id`. PK `(parent_id, child_id)`. Containment is a DAG, not a strict tree (a song may appear on a studio album and a compilation). Cycles are rejected.

**entity_ancestor** — closure table maintained by the core.
`entity_id`, `ancestor_id`, `depth`. Every entity has a self row at depth 0. PK `(entity_id, ancestor_id)`; index `(ancestor_id, entity_id)`. When a DAG gives two paths, keep the minimum depth.

**tag** — `id`, `parent_id` (nullable), `name`, `color` (nullable), `sort_order`, `description` (nullable; shown in tooltips and matched when finding tags, §7), `types` (nullable, core format 10, #135: the item types the tag may be applied to, as sorted space-separated type ids; `NULL` for every type; §7 *Tag types*). Sibling names are unique case-insensitively via a unique expression index on `(coalesce(parent_id, 0), lower(name))`; the `coalesce` is needed because SQLite treats NULLs as distinct in unique indexes, which would otherwise allow duplicate root-level tags (tag ids start at 1, so `0` is a safe sentinel). Tag operations in `tags.py` also check for clashes before writing so the UI can show a clear message; the index is the backstop. SQLite's `lower()` folds ASCII only, so the app-level check compares with `str.casefold()`. Names may repeat under different parents; the UI shows the full path when ambiguous.

**tag_alias** — `tag_id`, `alias`. Used for matching in the tag filter box and, planned (M20), for matching file keywords to tags (§7 *File keywords*).

**File keywords** (core format 11, #294, §7 *File keywords*): **entity_keyword** — `entity_id`, `resource_id` (the file that said it; both cascade), `match_key` (indexed; `core.keywords.keyword_key`: each level case- and accent-folded, levels joined by `/`), `keyword` (as written); PK `(entity_id, resource_id, match_key)`. **keyword_ignored** — `match_key` (PK). **file_tag_removal** — `entity_id`, `tag_id` (both cascade; PK both): a file-derived tag the user removed from that item. **entity_tag** gains `by_file` (bool, default false): the tag is there only because a file's keyword matched it; these rows are derived (§7).

**entity_tag** — `entity_id`, `tag_id`, `added_at`. PK `(entity_id, tag_id)`; index `(tag_id, entity_id)`. Only directly applied tags are stored; parent tags are never stored implicitly.

**field_provenance** — `entity_id`, `field`, `source` (`extracted`/`user`/`fetched`/`note`; `note` since core format 15, #379, which rebuilt the table since SQLite can't alter its CHECK constraint), `updated_at`. Extraction and fetching never overwrite a field whose provenance is `user` unless the user explicitly requests a refresh.

**Notes** (core format 15, #379, §9 *Notes*): **entity_note** — `entity_id` (PK, FK cascade), `folder_id` (where the note is looked for: the item's own folder, or the one a theme named with `ctx.note`; FK, set null), `resource_id` (the note file last read, FK, set null; both `NULL` for a note typed in Tagalot, #383), `size` and `mtime_ns` (the file's when read, so an unchanged note isn't read again), `body` (text), `updated_at`. **note_key_removal** — `entity_id` (FK cascade), `key` (case-folded); PK both: an Extra field from a note that the user removed from that item. Extra fields from notes are told apart by `field_provenance` rows named `extra:<name>` (source `note` or `user`); a value from a note has source `note` there and in the item's fields' rows. Snapshots and merges carry all of them.

**saved_search** — `id`, `name`, `definition` (JSON of the search model in §8).

**triage_dismissal** (core format 4, #110) — `list` (`unlinked`/`untagged`), `target_id` (a resource or entity id), `marker` (how it looked when dismissed), `dismissed_at`. PK `(list, target_id)`. No foreign keys: rows of things since deleted are ignored (§12 Triage).

**entity_merge** (core format 7, #120) — `merged_id` (PK), `type`, `ingest_key`, `into_id`, `merged_at`; index `(type, ingest_key)`. One row per item merged into another (§13). No foreign keys: the merged item is gone, and the row outlives the kept one. A later merge of the kept item repoints earlier rows at the new kept item, so `into_id` always names the item one step away. New entities are numbered past every merged id (`ingest.next_entity_id`), so a row never names a living item.

**dedupe_dismissal** (core format 8, #121) — `kind` (`exact`/`similar`), `key` (a group's fingerprint in hex, or a pair's two entity ids, lower first), `marker` (a group's resource ids; empty for a pair), `dismissed_at`. PK `(kind, key)`. What the user marked as not a duplicate (§12 Dedupe). No foreign keys: rows naming things since gone are ignored.

**user_relation** (core format 9, #260) — `name` (the relationship), `a_id`, `b_id` (FKs to `entity`, cascade), `added` (true: the user related them; false: the user removed it), `at`. PK `(name, a_id, b_id)`. The user's hand edits to relationships, which scans respect (§9 ingest context). Whole-item snapshots carry an item's rows, so undo restores them, and a merge moves them to the kept item.

**user_contains** (core format 13, #329) — `parent_id`, `child_id` (FKs to `entity`, cascade), `added` (true: the user put the child in the container; false: the user took it out), `at`. PK `(parent_id, child_id)`. Containment changed by hand (projects), which scans respect: a theme's `uncontain` leaves an edge the user added, and its `contain` doesn't restore one the user removed. Snapshots and merges carry it.

**online_response** (core format 14, #339) — `url` (PK), `status` (the HTTP status; 404 and other answers that aren't details are kept too, so an unknown identifier isn't asked about again), `body` (text), `fetched_at`. What online services answered (§9 *Online details*); **Look up online** replaces an item's answers. Not part of snapshots: it is a cache of the services, not of the user's work.

**user_order** (core format 12, #317) — `name` (an ordered relationship), `b_id` (FK to `entity`, cascade), `at`. PK `(name, b_id)`. The user put `b_id`'s items of that relationship in order by hand (Move up / Move down): scans then leave their positions alone, and items the files add go last. Snapshots and merges carry it.

**entity_merge_resource** (core format 7, #120) — `merged_id` (FK to `entity_merge`, cascade), `resource_id` (FK, cascade, indexed), `role`. The links a merged item had from its theme, so `ctx.entities_of` still finds it from those files (§9).

**schema_version** — `component` (`core` or theme id), `version`.

**Core schema versions** follow the same rule as theme versions (§9). The core version is kept both in `keep.toml` (`format_version`) and in `schema_version`. On open: a newer version in either place is refused with a clear message before anything is changed; an empty database gets the core tables and a `core` row; an older database raises a distinct "needs migration" error so the launcher can ask the user. Once the user confirms, `keep.db` is copied with SQLite's backup API (safe with WAL) to `keep.db.v<old>-<timestamp>.bak`, every migration step runs in one transaction (all or nothing), and `keep.toml` is updated. The backup is kept even if the migration fails.

Core format history: **1**, the initial schema; **2**, `tag.description` (#192, one `ALTER TABLE … ADD COLUMN`).

**entity_fts** — FTS5 virtual table for text search (§8), one row per entity, `rowid = entity.id`. Columns `title` and `body` (the entity's `search="text"` field values plus `extra` values, joined with spaces; and its note's body, #379). Tokenizer `trigram remove_diacritics 1`. Maintained by the DB writer, not triggers.

### Theme tables

Each theme entity type has its own table whose primary key `id` is also a foreign key to `entity.id` (joined-table layout). Its columns are real, typed columns (dates, numbers, strings) so they sort, index, and range-filter correctly. Theme classes are plain declarations; the core builds these tables as SQLAlchemy Core `Table` objects when a keep is opened (§9 Mapping and isolation). They are not ORM-mapped classes. Core tables are ordinary module-level ORM models. Relationship link tables declared with `related()` (§9) are built the same way, named `<theme id>_<relationship name>`.

Building them (`core/theme_schema.py`, `build_theme_schema(theme)`):

- **Types:** `str` → TEXT, `int` → INTEGER, `float` → REAL, `bool` → BOOLEAN, `date` → DATE, `datetime` → UTC-aware timestamp (like core tables); `| None` makes a column nullable.
- **Missing values:** ingest may create an entity without every field, so non-nullable `str`/`int`/`float`/`bool` columns have database defaults (`''`, `0`, `0.0`, false). A non-nullable `date` or `datetime` has no sensible default and is rejected: declare it `| None`.
- **Keys and indexes:** each entity table's `id` is its primary key and references `entity.id` with `ON DELETE CASCADE`. Link tables have `(a_id, b_id)` as the primary key, both cascading, plus an index on `b_id`; `many=False` adds a unique constraint on `b_id`. Fields with `search="range"` or `"choice"` are indexed; `"text"` fields rely on `entity_fts`.
- **Namespacing:** table names must start with `<theme id>_` and type ids with `<theme id>.` (overrides included), and may not reuse core table names; the theme id must be a lowercase identifier. Field names `id` and names starting with `_` are reserved.
- **Errors:** every problem found in a theme is collected into one `SchemaBuildError`, so its author sees them all at once; an entity with a conflicting table name still has its fields checked but gets no table.

### Fingerprints

`fingerprint = blake2b(size || first 64 KiB || last 64 KiB)`, computed lazily in background workers for files only. Precisely: a 16-byte (128-bit) blake2b digest over the size as 8 bytes little-endian, then the first and last 64 KiB; files of at most 128 KiB are hashed whole, once. Files are hashed 8 at a time (`fingerprint.THREADS`; #273), with results in queue order and errors reported from the scan's own thread: on a share, opening a file is milliseconds of latency, and threads overlap it. Workers skip files whose size or mtime changed since they were queued, and the stored value is written only if the row's size and mtime still match what was hashed, so a fingerprint never attaches to a newer version of a file. Files are queued newest first so move detection has what it needs. It is used to:

1. Reattach entities to files that were moved or renamed (a "new" resource whose fingerprint matches a "missing" one takes over its links; §6).
2. Find exact duplicates for the dedupe view (§13).

It is not a cryptographic identity of the whole file; when an exact match matters (dedupe merge), the UI can offer a full-hash verification.

## 6. Scanning and ingestion

A scan runs per root in background workers:

1. **Reachability check.** If the root is unreachable, mark the root offline and its resources `offline`, then stop. A root is reachable when its path on this machine (after per-user overrides) is a folder that can be listed within 10 seconds; an unreachable share can otherwise block for a minute. Missing paths, non-folders, permission errors, and timeouts all count as offline, each with its own `root.last_error`. Only `ok` resources become `offline`; `missing` ones stay `missing`, and nothing is deleted. When the root is reachable again, the scan's diff sets each resource back to `ok` or `missing`.
2. **Walk** with `os.scandir`, applying root exclude patterns and the theme's accepted extensions and directory rules. Directories are recorded as resources when the theme asks for them (for example, album folders). Details:
   - **Exclude patterns** match the POSIX relative path, case-insensitively on every OS (so a portable `keep.toml` behaves the same everywhere). `*` and `?` stay within one path segment, `**` spans segments, `**/x` also matches `x` at the top level, and `x/**` matches the folder `x` itself, so excluded folders are pruned without being read.
   - **Symlinked folders and junctions are not followed** (no loops, no escaping the root); symlinked files are included.
   - **Unreadable folders or files** are reported with their relative path and skipped; the walk continues.
   - Entries are yielded in name order within each folder, so a walk is deterministic.
3. **Diff** against the database by `(root_id, relpath)`:
   - New path → insert resource.
   - Existing path with changed `size`/`mtime` → update and clear fingerprint (recomputed later) and invalidate thumbnails.
   - Path not seen → mark `missing`, unless the walk now leaves it out (#152, `scanner.walk_scope`): excluded itself or under an excluded folder, a file whose extension the theme no longer takes, or a folder the theme no longer records. Those are flagged `skipped` (`resource.skipped`, core format 5) with their status left as last seen, since the file may well still be there. That includes files an older scan wrongly marked `missing`. Skipped files aren't ingested; they aren't listed in Triage's unlinked files, don't make an item count as having all files missing, and are counted per root (Keep configuration, scan summary). A skipped path that's in scope and seen again is back to `ok`, no longer skipped.
   - A path seen again after being `offline` or `missing` → back to `ok`, keeping its id (and its fingerprint if size and mtime are unchanged).
   - Paths at or under a folder the walk could not read are left as they are, not marked `missing`: not being able to look is not the same as the file being gone.
   - `last_seen_at` moves only for resources the walk actually saw; `root.last_scan_at` records the completed scan. Nothing is deleted.
   - The diff itself is a pure function of the stored rows and the walk; the DB writer applies it in batches and gets back the new resource ids for move detection and ingest.
4. **Move detection.** For new resources whose fingerprint matches a resource marked missing, transfer entity links to the new resource and delete the stale row. Fingerprints are computed for new files first so this step has what it needs. Rules:
   - A *new* resource is an `ok` file with a fingerprint and no entity links yet; a new file that already has links is a copy, not a move, and is left for dedupe (§13).
   - Missing resources in any root match, with no time limit (a file restored from a backup months later is still the same file). A missing file that was never fingerprinted cannot be matched.
   - When several missing and new resources share a fingerprint, they are paired only where the file name decides uniquely; anything still ambiguous is logged and left alone rather than guessed.
   - Role links, `entity.thumb_resource_id`, archive members, and the original `first_seen_at` move to the new resource.
5. **Ingest.** New and changed resources are passed to the theme's ingester in batches. The ingester creates or updates entities, role links, containment edges, and extracted field values (respecting provenance). Details:
   - `resource.ingested_at` marks what the theme has handled; it is cleared when a file changes and set only when its ingest commits. Every scan ingests all *pending* resources (new, changed, or whose ingest failed before), so a failure is retried by the next scan.
   - Batches of 100 run as one DB-writer transaction each: the theme's `ingest()`, `ctx.flush()` (containment, search index), and marking the batch ingested. A batch that raises is rolled back and each resource retried alone; resources that still fail stay pending and are listed in the scan report with the error.
   - With a theme, the walk uses the theme's `extensions` and `dirs`.
   - **Theme options** (#82): each root records, in `root.ingest_options`, the option values (§9) it was last ingested with. When the values in effect differ at the next scan, every resource of the root is marked pending and ingested again, so the theme can regroup (assets2d's artists). A root with nothing recorded counts as ingested with the defaults.
   - **Theme version** (#118): the record also holds the theme's version, written only past version 1, so records made before this still match. A theme whose version went up may read more from files (assets2d 2 reads a picture hash), so each root is read again once, at its next scan, after the usual upgrade prompt.
   - **Reading files happens before the transaction** (#176): for each batch the scan worker first calls the theme's optional `prepare(batch)`, outside any transaction, which returns `{resource id: value}` (tags, image sizes, font names); `ingest()` then reads each value with `ctx.prepared(resource)`. So the write lock is held only for database work, and tagging stays responsive while a batch is read from a slow share. If `prepare()` raises, the batch is prepared one resource at a time; a resource that still fails is reported with the error and left pending. Themes without `prepare()` skip the step (no "Reading…" progress). Since #274 `prepare` runs on 8 reading threads (`scanjob.PREPARE_THREADS`), 10 resources per call (`PREPARE_CHUNK`), and the next batch is read while the writer ingests the current one; results and errors are gathered back in order on the scan's thread. So `prepare` keeps its state local to each call.
6. **Closure maintenance.** The core updates `entity_ancestor` for changed containment edges.
7. **Thumbnail queue** (#241, `core/thumbnails/queue.py`). After a scan, its thumbnails are made in the background, so they're ready before anyone browses (unless the keep turns this off, `[thumbnails] after_scan = false`). The queue is every entity with no remembered thumbnail source (ingest clears it whenever links change, and new entities have none), plus those whose remembered file was ingested again since the scan began (changed in place); newest first. The session's queue resolves them as a grid would (§10), 4 at a time (`queue.THREADS`, #275; one thread runs the list and hands each thumbnail to the pool, in roughly the list's order), while grids keep their own 4 workers, so what's on screen isn't kept waiting. The next scan replaces a run in progress; closing the keep stops it first. The status bar shows "Making thumbnails: N left", and grids pick up the results when it finishes.

### Closure maintenance

`entity_ancestor` stores minimum depths over a DAG, so removing an edge can drop an ancestor or lengthen its shortest path, and the table alone cannot tell which (path counts would fix membership but not minimum depth). The core therefore uses one strategy for every containment change (edge add/remove, entity delete, entity merge, reparent):

1. **Collect affected nodes** before changing edges: for each changed edge `p → c`, all descendants of `c` (including `c`) from the current closure. Only these can gain or lose ancestors; rows whose ancestor is itself inside the affected set cannot depend on the changed edge (that would require a cycle).
2. **Apply the edge changes** to `entity_contains`.
3. **Recompute** the affected nodes' rows: delete them, then rebuild them with one recursive CTE that walks `entity_contains` upward and keeps `min(depth)` per `(entity_id, ancestor_id)`. The CTE has a depth cap (64) as a guard against corrupt data.

Because recomputation reads edges, not the closure, the order of changes within a batch does not matter. Performance: an edge into an entity with no children can't close a cycle, so the recursive cycle check runs only when the child already has children; accepted edges are inserted in batches. During ingest most children are new leaves, which took adding 52k edges from 20 s to 0.7 s. The DB writer calls `closure.apply(added, removed)` once per batch, in the same transaction as the edge changes. Containment is shallow, so affected sets are small (one song, or an album plus its tracks). An incremental upsert for additions is a possible later optimization, not part of v1.

- **Cycle check:** an added edge `p → c` is rejected if `p == c` or `c` is already an ancestor of `p`; edges in a batch are checked in order, each against the graph including the previously accepted ones. A rejected edge (a theme ingester bug) is logged with the resource path, surfaced in the activity panel, and skipped; the scan continues.
- **`rebuild_all()`** recomputes the whole table. It is exposed as a repair action and is the oracle for tests: randomized sequences of adds and removes must leave the incrementally maintained table identical to a full rebuild. **`verify()`** computes the correct table with the same query and reports missing and extra rows without changing anything. **`maintenance.repair_indexes()`** is the one repair action for derived data: it checks, then rebuilds, both the closure and the search index, and reports what was wrong.
- **Depth semantics:** because depth is the minimum, `depth = 1` means exactly "direct child" and `depth = 0` is the self row.
- **API** (`core/closure.py`): `apply(conn, added, removed)` applies removals first, then additions in order (each checked for cycles against the edges as they stand, including earlier additions in the batch), and returns what was added, removed, and rejected with a reason. Existing edges and missing ones are skipped. `add_entities(conn, ids)` gives new entities their depth-0 self row, which inheritance queries need even without edges. `detach(conn, ids)` removes every edge touching the entities and must run before they are deleted: the foreign-key cascades remove their own rows but not transitive ones (in A → B → C, deleting B would leave C under A). Affected ids go through a temporary table, so batch size isn't limited by SQLite's bound-parameter limit.

`core/scanjob.py`'s `scan_root()` runs steps 1–4 for one root in a worker and returns a report (counts, moves, read errors) for the activity panel. Within a scan, each pending file of the root is fingerprinted at most once, so an unreadable file can't loop, and move detection considers only that scan's new files. Steps 5–7 join it with themes (M4) and thumbnails (M8).

Scans are incremental and resumable. File-system watchers are not relied upon because they are unreliable on SMB; rescans are manual or scheduled per keep.

### Threading model

- Workers (a `QThreadPool`) do file-system I/O, hashing, metadata extraction, archive reading, and image decoding.
- Workers never write to the database directly. They send result batches to a single **DB writer** that applies them in short transactions, which avoids SQLite write contention.
  The writer (`core/writer.py`) is one thread that owns the write engine. A job is a function taking a connection; each runs in its own transaction, in submission order, and the submitter gets a `Future` for its result (the UI converts these to signals). A failed job rolls back only itself. Large scans are split into parts of at most 500 changes, each its own transaction; an interrupted scan is completed by the next one because the diff is recomputed.
- Read queries for the UI use their own connection. Anything that may take more than a few milliseconds (large searches, counts for the dashboard) runs off the GUI thread and posts results back via signals.
- The GUI thread must never block on file-system or network I/O.
- **An open keep** is a `KeepSession` (`core/session.py`): opening does `keep.toml`, the core schema, theme resolution, the theme schema, then starts the DB writer, a read-only engine, the tag tree cache, and the tag service; `close()` shuts them down. Opening does I/O and may migrate, so the UI calls it from a worker. `scan_all(progress)` scans every root with this machine's root paths.
- **Qt glue** (`ui/workers.py`): `run_in_pool(fn, on_done, on_error)` runs work on a `QThreadPool` and `watch_future()` watches a DB-writer future; both call back **on the GUI thread** through a relay `QObject` living there, since a signal connected to a plain Python callable would run it in the emitting (worker) thread. `ScanController` runs "Scan now" one scan at a time and re-emits `scan_root`'s progress messages on the GUI thread. **Quitting** waits (up to 30 s) for pool jobs, such as a keep still closing, to finish before `run()` returns; a job whose relay is already gone drops its result instead of raising.

## 7. Tags

- Tags form a tree. Depth is expected to be shallow (a handful of levels), and tag counts in the hundreds to low thousands. The full tree is cached in memory and invalidated on change. The cache holds an immutable snapshot (`TagTree`: children in display order, memoized subtrees, paths, aliases, case-insensitive sibling lookup, filter-box matching); tag operations invalidate it after they commit, and readers holding an older snapshot are unaffected.
- **Search semantics:** selecting a tag means "this tag or any of its descendants."
- **Applying a child tag never stores its parent.** Expansion at query time makes the parent match.

### File keywords

Built in #294 (the core) and #295 (everything you see). Designed in review. Files often carry their own tags: front matter's `tags`, EPUB subjects, ComicInfo genres, PDF keywords. They become Tagalot tags only by matching tags you defined, so the tag tree never fills with every spelling a file used:

- **Themes report keywords** (`ctx.keywords(entity, resource, keywords)`, §9): what one file says about one item, replacing what that file said before. An item's keywords are those of all its files.
- **Matching** (`core/keywords.py`, `keyword_index`): a keyword matches a tag when it equals the tag's **full path** (written `Genre/Fantasy`, `Genre > Fantasy`, or as Tagalot shows paths), one of its **aliases**, or its **name** when no other tag has that name, ignoring case and accents. Paths win over aliases, and aliases over names; an alias or a name two tags share matches neither. An item gets the tags its keywords match, if the tag's types allow the item (§7 *Tag types*); nothing creates a tag.
- **File tags are derived** (`apply_file_tags`): the `by_file` rows are a function of the keywords, the tag tree (paths, aliases, types), and the removal records, recomputed for the items a scan touched (at the ingest flush) and for every item after a tag operation and its undo or redo. Undo history records only the user's own rows (and removal records), never file tags, so undo can't turn one kind into the other. A tag the user also applied by hand is the user's row and is never touched; a merge carries file tags and removal records to the target.
- **Mapping is aliasing:** tying an unmatched keyword to a tag adds it as that tag's alias, so it matches from then on, for every item, and also finds the tag in the filter box. Renaming, merging (the old name becomes an alias, §7 operations), and deleting tags, and editing aliases, re-apply file tags; each is undoable as usual. Deleting a tag sends its keywords back to unmatched.
- **Tags from files are marked** (`entity_tag.by_file`) and shown so in the tagging panel. A scan re-applies them as the files change: a keyword gone from every file takes its tag away, unless the user also added the tag by hand.
- **Removing one by hand sticks:** it is remembered for that item (`file_tag_removal`, recorded with the removal's undo step), so later scans leave it off; undoing the removal brings it back as a file tag; the item's page offers **Restore**; adding the tag back by hand clears the record.
- **Finding unmatched keywords:**
  - a scan that finds new ones says so in the status bar ("… 2 new file keywords don't match a tag.") and in the Activity panel, with a **Review** link to the page (the window remembers the unmatched keys it last counted, so only new ones are reported);
  - TOOLS → **File keywords (7)** counts them while any are unmatched (`unmatched_keys`), recounted after scans and tag changes;
  - the **File keywords** page (`ui/keywords_page.py`, `keyword_report`) lists each keyword with its item count and up to three example titles, most-used first, filtered by **Show** (Unmatched, Matched, Ignored, All): **Map to tag…** (the tag picker; several selected keywords map to one tag as one undo step, `TagService.map_keywords`), **Create tag…** (at a path you confirm, starting from the keyword with its `/` levels as `>`; the keyword becomes its alias only if it wouldn't match the new tag anyway), or **Ignore** / **Stop ignoring** (`keyword_ignored`, one undo step); double-clicking maps. Mapping may make a keyword the alias it already is by name (`add_alias(allow_name=True)`): that is how a name two tags share is tied to one of them;
  - an item's page has a **From the file** section (`item_keywords`): each keyword and what became of it: the tag it gives, "removed from this item" with **Restore** (`TagService.restore_file_tag`, undoable), "not for this type" (the tag's types exclude the item), *Ignored* with **Stop ignoring**, or *No tag* with **Map…** and **Ignore**;
  - Triage gains **Unmatched keywords** (`SearchSpec(triage="keywords")`; the condition takes the tag tree, since matching does): items with a keyword that matches no tag and isn't ignored, with a button to the File keywords page;
  - lists in a keep whose files give keywords (`KeepSession.has_keywords`, rechecked when keywords are recounted) offer a **Keywords** column beside Tags (hidden by default; shown by default in Unmatched keywords, asked for in review): the item's keywords, unmatched ones first, with a tooltip saying what each gives ("Jazz → Mood › Calm", "Rock: no tag");
  - the tagging panel shows a tag in *italics* when every selected item that has it has it only from its files (`file_tag_counts`), and its tooltip says how many; the tag manager's **Used on** says how many of a tag's uses come from files (`TagUsage.from_files`).

### Tag types

A tag can be limited to some item types (#135; decided in review): Genre for books and comics, but not authors.

- **Set on any tag, inherited down:** a tag's own `types` (§5), else every type; a sub-tag's types are what it and all its ancestors allow (`TagTree.scope`, an intersection), so a sub-tag can only narrow its parent's. Reparenting under a limited tag narrows accordingly.
- **Setting them** (`set_tag_types`, `TagService.set_types`, one undoable step with the rest of the tag row): the tag manager's **Applies to** row says "Every type", "Books and Comics", or "Comics (from 'Genre')" when a parent decides, and **Change…** opens a dialog: every type (its parent allows), or only the ticked ones. If the tag or a sub-tag is on items of types it would no longer allow, the window counts them (`scope_conflicts`) and **asks before removing it from them**; the removal is part of the same undo step.
- **Tagging** (`tag_entities`, `TagService.apply_counted`) applies a limited tag only to items of its types and reports the rest; the status bar says so ("Tagged 3 items with 'Fantasy'. Skipped 2 Authors: 'Fantasy' is for Books and Comics.").
- **The tagging panel hides** the tags none of the selected items' types allow (the selection summary also reads their types), unless a selected item already has one, so it can still be removed; with nothing selected every tag shows.
- **Unaffected:** searching and filtering (any tag can be searched for anywhere, and inherited tags still count through containment), tag counts, and uses made before a limit was set by a merge or a move (merging into, or moving under, a limited tag keeps existing uses).

### Tag operations (tag manager)

| Operation | Behavior |
|---|---|
| Add | Create under the selected tag or at root level. |
| Rename | Must stay unique among siblings (case-insensitive). |
| Reparent | Drag-and-drop or "Move to…" picker. Moving a tag under itself or a descendant is rejected. Show the affected item count. |
| Merge | Fold tag A into tag B: reassign all `entity_tag` rows (deduplicating), move A's children under B, add A's name as an alias of B, delete A. |
| Delete | If the tag has children, ask: delete the subtree, or move children up to the deleted tag's parent. Show how many entities lose a tag. |
| Aliases | Alternate names that match in the filter box only. |
| Color | Optional, shown on chips. |

Details the table leaves open:

- **Descriptions** are optional free text (trimmed; blank clears; at most 2,000 characters), set with `set_tag_description` / `TagService.set_description` (undoable). Tooltips show them in the tagging panel, filter-bar suggestions, and chips. Merging keeps the target's description, or takes the source's if the target has none. They are edited in the tag manager (M7).
- Names are trimmed with inner runs of spaces collapsed, must be non-empty and at most 200 characters, and compare with `str.casefold()` among siblings. Renaming a tag to a different case of its own name is allowed. Colors are `#rrggbb`.
- **Finding tags** (the tagging panel's filter, the filter bar's suggestions) matches a tag's name, aliases, and **description** (§5), ignoring case **and accents**, like the search box. A tag found only through its description is shown with a short excerpt around the match (`Iceland — …road trip around the…`, `tags.description_excerpt`), and ranks after name and alias matches in suggestions. Items are not found through their tags' descriptions; the search box matches only their own text. Examples of accent folding: `isl` finds the alias "Ísland", `arger` finds "Ärger" (`tags.search_key`: casefold, then drop combining marks after NFKD). Names themselves stay distinct by case-folding only, so "Ärger" and "Arger" can be siblings.
- New and moved tags go to the end of their new parent's children.
- **Reparent** is also refused when the new parent already has a child with the same name.
- **Merge** is refused into the tag itself or one of its descendants (that would create a cycle); merging into an ancestor is fine. A child of A whose name clashes with a child of B is merged into it recursively, since merging is what the user asked for. A's aliases move to B along with A's name, skipping any that duplicate B's name or aliases.
- **Delete, promoting children:** refused, with the clashing names listed, if a child's name clashes with a tag at the level above; the user didn't ask for a merge, so none is done silently. Deleting a subtree removes its tags from entities; entities are never deleted.
- Each operation re-reads the tree inside its own transaction to validate, never trusting a possibly stale cache, and the cache is invalidated after it commits.

All tag operations are single transactions and are recorded in an undo stack for the session.

**Tagging entities** (`tag_entities` / `untag_entities`, `TagService.apply` / `remove`) adds or removes exactly the given tags on the given entities, in batches of 500, skipping pairs that already exist (or don't) and entities that no longer exist; parents are never added. Each call is one undo step that records exactly the rows it added or removed (never every use of a tag, so it stays cheap for tags on tens of thousands of items); a call that changed nothing isn't recorded. The UI runs these on a one-thread pool (`ui/tag_actions.py`), so undo history keeps the order the user acted in.

**Undo/redo** (`core/tag_service.py`): each operation's transaction also records the full `tag` and `tag_alias` tables before and after it (they are small, and only tag operations write them) and the `entity_tag` rows it removed and added within its scope (both subtrees for a merge, the subtree for a delete). Undo restores the "before" tables and reverses that delta; redo restores "after" and replays it. Neither re-runs the operation, so redo can't fail validation. Tagging done after an operation is kept when it is undone; the one exception is undoing the creation of a tag, which removes that tag (and so its uses) again. The history holds 100 steps and is cleared by a new operation after an undo, as usual.

## 8. Search

### The search model

A search is an immutable, hashable value object, serializable to JSON (used for saved searches and view state). Tuples rather than lists keep it hashable, so it can key result caches.

```python
@dataclass(frozen=True)
class SearchSpec:
    types: tuple[str, ...] = ()           # entity types in scope; empty = all
    include: tuple[int, ...] = ()         # tag ids; each must match (AND)
    exclude: tuple[int, ...] = ()         # tag ids; any match removes the item
    fields: tuple[FieldFilter, ...] = ()  # typed filters, only for fields every scoped type has
    within: int | None = None             # entity id: restrict to its descendants
    related: tuple[str, int] | None = None  # (relationship, entity id): items related to it, from either side (#125)
    text: str | None = None               # matches title and text-search fields (trimmed; blank = None)
    inherit_tags: bool = False            # tags on ancestors count
    show_contained: bool = False          # also list descendants of matching containers
    aggregate_up: bool = False            # containers match if any descendant matches
    nest: bool = False                    # leave out matches held by another match (tree layout)
    triage: str | None = None             # a triage list: "untagged" or "missing" (§12)
    sort: tuple[SortKey, ...] = (SortKey("title"),)

FieldFilter = TextFilter(field, text, match) | RangeFilter(field, low, high) | ChoiceFilter(field, values)
SortKey(field, descending=False)
```

One filter kind per `field(search=...)` kind (§9): `TextFilter` compares case-insensitively, with `match` either `contains` (anywhere in the value; the default) or `starts_with` (at the start of the whole value, so "The" matches "The Beatles" but not "Abbey Road: The Remaster"); `RangeFilter` bounds are inclusive and either may be open (`None`); `ChoiceFilter` matches any of its values. The JSON form carries `"version": 1`; dates and datetimes are tagged (`{"$date": "1997-09-22"}`) so they round-trip as dates; missing keys take defaults and unknown keys are ignored; a newer version is refused with a clear message.

### Semantics

- Each included tag is expanded to itself plus descendants, forming one group; **every group must match** (AND across groups, OR within a group).
- All excluded tags are expanded and merged into one set; **matching any excludes the item**.
- **Inheritance (`inherit_tags`)** changes matching: an entity's effective tags are its own plus those of all its ancestors. This applies to exclusion too: excluding "Christmas" removes every song of an album tagged Christmas.
- **Show contained (`show_contained`)** changes display: descendants of matching containers are also listed (as expandable children in tree/grouped layouts).
- **Aggregation (`aggregate_up`)**: a container matches if any descendant matches. Off by default; the filter bar's **By contents** toggle (#133, §12), which a view can start on (`SearchView(aggregate_up=True)`).
- **Nesting (`nest`)**, for the tree layout's top level: a match that another match holds, at any depth, is left out, because expanding that container shows it (Browse with albums and songs in scope lists the albums, with their songs under them, and only the songs that have no matching album at the top). Ignored with `show_contained`. The search page sets it whenever it shows the tree.
- **Within** restricts results to descendants of one entity (used by drill-down chips and container detail pages).

How they combine (the design above leaves these open):

- **Within** means strict descendants (depth ≥ 1); the entity itself is never listed.
- **Aggregation** lets a container match on tags and text through a descendant that is not itself excluded. Field filters always apply to the listed entity, since they belong to its type, and the container's own exclusion always applies: an excluded album is not brought back by a matching song. With no include tags and no text there is nothing to aggregate, and the toggle has no effect.
- **Show contained** lists the matches plus every descendant of a match, regardless of `types` (that is the point: search albums, see their songs) and without re-applying include, text, or field filters to those descendants, which are shown because of their container. Exclusion still applies to them, as §8 says matching any excluded tag removes the item. Each entity is listed once even when two matching containers share it.

- **Deleted tags** (for example in a saved search) count as a subtree of just themselves: including one matches nothing, excluding one excludes nothing.
- **Field filters** resolve field names through a mapping of columns: the core provides `title`, `created_at`, and `updated_at`; themes add theirs (§9). An unknown field is an error, never ignored.
- **Theme fields in scope** (`core/search_fields.py`) are the fields every scoped type declares with the same value type (an empty scope means every type). Each becomes a scalar subquery on its type's table, looked up by primary key (combined with `coalesce` across several types), so filtering and sorting on it needs no join. Sorting 50k files by `modified` takes about 15 ms for the first page plus the count; a range filter on `size`, about 35 ms.
- **Sorting** follows `sort`, compares titles case-insensitively, and always ends with the entity id, so paging never skips or repeats an item.

### Query shape

With inheritance, each include group becomes:

```sql
EXISTS (
  SELECT 1 FROM entity_ancestor a
  JOIN entity_tag t ON t.entity_id = a.ancestor_id
  WHERE a.entity_id = e.id AND t.tag_id IN (:group)
)
```

Without inheritance, add `AND a.depth = 0` (or query `entity_tag` directly). Exclusion is the same pattern under `NOT EXISTS` with the merged exclude set. Field filters become ordinary `WHERE` clauses on the joined theme tables. SQL is built with SQLAlchemy Core expressions, never string concatenation.

### Text search

The search box uses the `entity_fts` table (§5) with the FTS5 **trigram** tokenizer, so text matches **substrings** ("bey" finds "Abbey"), case-insensitively and ignoring diacritics ("beyonce" finds "Beyoncé").

- **Query building:** the user's input is split on whitespace; each term is double-quoted (internal quotes doubled) and the terms are ANDed. Users never see FTS query syntax, and stray quotes or words like `AND` cannot cause syntax errors. Before that, `SearchSpec` cleans the text: control characters (including NUL, which FTS5 treats as the end of its query) become spaces and unpaired surrogates are dropped.
- **Short terms:** trigram matching needs at least 3 characters. Terms of 1–2 characters fall back to a `LIKE` scan over `entity_fts` (about 10 ms at 50k entities), with `%` and `_` escaped. `LIKE` ignores case for ASCII letters only and does not fold diacritics, so a 2-letter non-ASCII term is matched exactly.
- **Sync:** whenever an entity's title, text-search fields, or `extra` change (ingest, user edit, merge, delete), the DB writer rewrites that entity's `entity_fts` row in the same transaction (`core/fts.py` `sync_entities`). `body` is the text-search field values then the `extra` values, flattened: nested lists and objects contribute their values (not keys), numbers become text, booleans and nulls are skipped. Theme text fields arrive through a callback once themes exist. A "Rebuild search index" action (`rebuild_search_index`) repopulates the table from scratch, and `index_is_consistent` is a cheap health check.
- **Field filters** (a `search="text"` field in the filter bar) use ordinary `LIKE` on their own column; FTS is only for the global text box.
- **Size:** measured at roughly 20 MB of index per 50k entities (about 5× a word-based index). This is accepted; it is small next to `thumbs.db`.

### Search inside documents (M23, #308; designed in review)

Finding documents (papers, books) by what they say, not only by their details. It is a separate index from the search box's (`entity_fts`), and separate from keywords: keywords are for tagging, this is for finding. Decided in review, 2026-10-06:

- **Which files** (chosen: the theme marks types, over themes extracting text themselves or every readable file): an entity type with `full_text = True` (theme API version 6; the research theme's Paper, the books theme's Book) is a document type, and the files in its primary role are read. The core reads them by format with the shared readers: `read_document_text(path)` (in the API, so themes can use it) gives a file's text **as pages**: a PDF's pages, an EPUB's spine documents (its chapters, numbered in reading order), and one page for Markdown, DOCX, ODT, and plain text. A theme can read some files its own way with `Theme.document_text(resource)` (pages, or `None` for the core's reader). Comics, link files, and Pages files have no text to read.
- **When** (chosen: in the background after scans, over during the scan): like thumbnails (§6 step 7), after a scan the document files that are new or changed since they were last read (size and modification time) are read on two reading threads, with **Reading contents: N left** in the status bar; a scan stays as fast as before, and a document is found by its contents once it has been read. Nothing is read while the keep's contents search is Off.
- **Where the text lives:** `fulltext.db`, a second SQLite database beside `keep.db`, so the main database stays small and this one can be deleted and rebuilt. Its tables: `contents_file` (resource id, size and mtime when read, when, how many pages, an error if it couldn't be read) and `contents_page` (resource id, page number, text). The text is stored once; the index is an FTS5 table over `contents_page` (external content, so the text isn't stored twice). It has its own writer thread: the one-writer rule (§6) is per database. A file whose resource is deleted loses its text; one missing or offline keeps it (rule 7).
- **The index type**, per keep, chosen when contents search is turned on (Keep configuration, Keep tab; and when a keep is made with a theme that has document types): **Off**, **Words** (the default: FTS5 `unicode61` with diacritics removed, whole words and word starts, `photosynth` finds "photosynthesis"; about the text's size), or **Substrings** (FTS5 `trigram`: text inside words, `synth` in "photosynthesis"; 3 to 5 times the text's size). Saved in `keep.toml` as `[contents] index = "words"` or `"substrings"` (absent: Off). Switching builds the new index from the stored text in the background, without reading any file again; searches use the old one until the new one swaps in, and the status bar shows the progress. **Off** drops the index but keeps the text, so turning it on again is quick; **Clear contents text…** deletes both.
- **Limits:** a file's text stops at 5 MB and a PDF at 2,000 pages (the rest isn't searchable; the file isn't refused). A file that can't be read is listed in the activity panel and isn't tried again until it changes, or until Tagalot's readers improve: `fulltext.db`'s `contents_meta` records the `READERS_VERSION` that last read every document, and a store read by older readers tries each failed file once more (#375). Rough costs per 1,000 papers: about 50 MB of text; reading, once, 1 to 3 minutes; an index rebuild, seconds to a couple of minutes.
- **Searching** (chosen: a toggle and snippets, over a separate page): an **In documents** toggle in the filter bar (named **Contents** in review, renamed in #351 so it doesn't read like By contents; shown when the keep's contents search is on) makes the search box look inside documents too: an item matches if its title or fields match, as now, **or** a page of one of its files contains every word (Words: each word, its last one as a word start; Substrings: each term, as now, with `LIKE` for terms under 3 characters). A paper matches when any of its versions does. The toggle is part of the search (`SearchSpec.contents`), so it is saved with views and saved searches. Ordering is unchanged (the view's sort), not by relevance.
- **Where it matched** (chosen: the item and page, over the item alone): matches name the file and page. List layout gets a **Match** column (on when Contents is on): a snippet around the first match, with the matched words in bold, and the file and page in its tooltip (`1706.03762v7.pdf, p. 8`; an EPUB's chapter as `ch. 3`). Grid cards show the snippet as a line under the title. Snippets come from FTS5's `snippet()` for the page that matched, fetched with each page of results. Opening a file at that page is for later.
- **As built: the text** (#348, `core/contents.py`, `themes/document_text.py`): `read_document_text` collapses whitespace, keeps empty pages (so page numbers hold), drops an EPUB's `head`, `script`, and `style`, and Markdown's front matter, and reads a Kindle book's chapters (its page breaks; API version 7, #370), which the Match column shows as `ch.` like an EPUB's; a PDF is read a page at a time under the PDFium lock, so a long one doesn't hold up thumbnails. `fulltext.db` is versioned with `PRAGMA user_version` and rebuilt from scratch for another version (it holds nothing that can't be read again); it is opened when first needed, so a keep that never searches inside documents has none. After each scan (when contents search is on), the window reads what's new or changed (`KeepSession.queue_contents`), first dropping the text of resources deleted since; a file that can't be read is recorded with its error and listed in the activity panel as **Text not read**. A `full_text` type needs a primary role and `api_version = 6`.
- **As built: the index** (#349): `contents_words` (`unicode61 remove_diacritics 2`) or `contents_substrings` (`trigram remove_diacritics 1`), FTS5 tables with external content (`content='contents_page'`, `content_rowid='id'`; `contents_page` has an explicit integer `id`, so a `VACUUM` never renumbers it: `fulltext.db` format 2). Building is FTS5's `rebuild` in one write of the contents writer, which then drops the other index and records the ready one in `contents_meta`; reading waits for it, and searches use the old index until it commits. Saving or deleting a file's text takes its old pages out of every index there is (an external-content index needs the old text to remove it) and adds the new ones, in the same transaction. The Keep tab's **Search inside documents** group (shown for themes with document types) has the Off / Words / Substrings choice, what is stored ("Text of 120 documents (3,402 pages, 48 MB); 2 couldn't be read"), and **Clear contents text…**, which asks first, then turns contents search off and deletes the text and the index. Turning it on or switching builds the index ("Building the contents index…" in the status bar), then reads what hasn't been read; so does opening a keep whose `keep.toml` asks for another index than the one built.
- **As built: searching** (#350, `core/search.py`): the keep's read-only connections attach `fulltext.db` as schema `contents` whenever it exists (`contents.attach_on_connect`), so one query matches items and documents' pages. With `SearchSpec.contents` (in its JSON form only when on), the text condition becomes "the item's title and fields match, **or** one of its document files has a page matching" (`contents_ids`, a materialized set like the other text set); a document file is a row of `entity_resource` in its type's primary role. The search functions take a `ContentsScope` (the built index and the document-file condition) from `KeepSession.contents_scope(conn, spec)`, which is `None` unless the spec asks, the keep searches contents, and an index is built: so a search asking for contents in a keep without them is an ordinary one. FTS5 needs its table unqualified in `MATCH` (`contents_words MATCH ?`, from `contents.contents_words`), so that one name is a literal column. Measured (2026-10-06, dev machine, `tests/core/test_contents_benchmark.py`: 1,000 documents of 50 pages, 50,000 pages, about 25 MB of text): building Words 0.4 s, Substrings 2.1 s; a rare word's first page and count 3 ms in either; a word on nearly every document 78 ms (Words) and 90 ms (Substrings). The filter bar's **In documents** toggle sits after By contents, hidden unless the keep searches inside documents and the page can list documents (Search all, or a page whose types include a document type: not an author's credits or an artist's page, #324); it is saved with a view's toggles and with saved searches, and pages refresh when contents search changes or documents finish being read.
- **As built: where it matched** (#351): `core.search.contents_snippets` finds, for the items on a page of results, the first matching page of their document files (by file path, then page) with FTS5's `snippet()` (about 12 words, the matched ones between control-character markers; 12 tokens with Words, 64 with Substrings, whose trigram tokens are about a character each, #352); a Substrings search of only short terms, which has no index match to cut a snippet with, gets an excerpt around the first term instead. The list's **Match** column comes right after the title when In documents is on and there is text; its cell is the snippet with the matched words in bold (a rich-text delegate), its tooltip the snippet and the file and page (`p. 8`, an EPUB's `ch. 3`, nothing for a one-page file). Grid cards end with the snippet as one more line, starting at the beginning of the first matched word (an ellipsis before it; a Substrings match inside a word starts at the word, #352), since a card's short line would otherwise cut the match off; their tooltip adds the whole snippet with the file and page. Search all's sections show the column too.
- **As built: the themes** (#352): the research theme's Paper and the books theme's Book are `full_text` types (both themes now `api_version = 6`); comics aren't (their pages are pictures). **New keep** offers **Search inside documents** (Off / Words / Substrings, Words selected) for a theme with document types, and the keep is created with that `[contents] index` (`create_keep(..., contents_index=)`); for other themes the row is hidden. The research and books demos turn it on and read their documents before opening, and their files have text to find: body sentences on two research PDFs, chapters in two books' EPUBs, and the demo's DOCX and ODT now carry real `word/document.xml` and `content.xml` text.
- Built in M23's tasks, #348 to #352.

### Global vs. scoped searches

- The core always provides a **global search** over all entity types. Results are grouped by type in collapsible sections with counts (`count_by_type`: one grouped query, types with no matches left out; about as fast as a plain count).
- Themes declare **scoped search presets** (Actors, Fonts, Albums). Field filters appear only when every type in scope has the field.
- Each view has defaults for `inherit_tags` and `show_contained`; user toggles override them and are saved per view in `ui_state.json`.
- Saved searches appear in the navigation list.
  - **Saving** (#127, `core/saved_searches.py`): **Save…** in any search's header (Search all, a view, an embedded contents or related search), or Edit → **Save search…** (Ctrl+S), asks for a name, starting from the page's title. A saved search remembers the page's own search (`base`: a view's types and toggles, with the sort chosen), its filter bar (`filters`, a `SearchSpec` of their own: tags, text, field chips, the Only type, the Within item with its title, the toggles), its layout, and whether it shows Search all's sections. Opening it rebuilds the page and its chips, so each chip can still be removed. On a saved search's page, Save (Ctrl+S) updates it in place without asking; **Save search as…** (Ctrl+Shift+S) asks for a new name. Names are unique ignoring case: saving under a taken one asks before replacing it. A row holding a bare search (older, or made by hand) opens with no chips.
  - **Managing:** right-click a saved search under SAVED for Open, **Rename…**, and **Delete** (its page closes). Saving, updating, renaming, and deleting are each one undo step (`SavedChange`); the list reloads after each, and after undo. Its remembered layout and columns live under `saved:<id>` in `ui_state.json`.

### Performance target

Tag + field searches over 50,000 entities return the first page in under 100 ms on a local SSD. Results are paged/lazily fetched by the Qt model.

Measured (2026-09, dev machine, `tests/core/test_search_benchmark.py`, 50,500 entities: 500 artists × 10 albums × 9 songs, 300 tags applied at every level, a DAG via compilations), median first page: everything by title 6 ms; a 90-tag subtree 12 ms; two groups 17 ms; excluding a subtree 17 ms; text 5 ms (2-letter `LIKE` 35 ms); inherited include/exclude 38/47 ms; within 1 ms; aggregate 5 ms; show contained 20 ms; all options at once ~105 ms. Counts cost about the same as a page. The benchmark asserts five times the target, so CI runners don't flake but real regressions fail.

What makes it fast: every test against a set (a tag group, the exclusion set, the text matches, the closure) is an uncorrelated `IN (subquery)`, so SQLite builds the set once from the `(tag_id, entity_id)` and `(ancestor_id, entity_id)` indexes; each distinct set is a `MATERIALIZED` CTE computed once per query; and aggregation first finds the (small) set of matching descendants, then their ancestors through the closure's key. The first version used correlated `EXISTS` and took 3.3 s for show-contained and 6.1 s for everything at once.

## 9. Theme API

### Discovery

- Built-in themes ship in `tagalot/builtin_themes/`.
- User themes are single `.py` files (or packages) in `user_data_dir("tagalot")/themes/` and in any extra directories from settings. They are loaded with `importlib`.
- Later, installed packages can register themes via the `tagalot.themes` entry-point group.
- **For theme authors** (#130): [docs/THEMES.md](THEMES.md) is the guide. `tagalot --new-theme ID [--name NAME]` copies the template theme (`themes/template.py`, a working Group ⊃ Item theme with every place to change marked `TODO`, kept valid by its own tests) into the user themes folder with its id, name, and class name filled in, refusing an id already taken or a file already there. `tagalot --check-theme ID_OR_FILE` imports and validates one theme as the launcher would (`loader.load_theme_file`) and prints `ok` or each problem (`theme_tools.py`). It takes a path, or an id: `<id>.py` (or a `<id>/` package) in the user themes folder and settings' extra folders, else the theme declaring that id (a built-in one is reported as built in); with no match it says where it looked and lists theme files that didn't load, since a broken file can't say its id. The template ships as a data file in packaged builds, so `--new-theme` works there too (`--check` reports it). Themes are loaded afresh whenever a keep opens, so an author's loop is edit, then close and reopen the keep; `reload_theme()` (below) isn't wired to the window yet.
- A theme module exposes exactly one `Theme` subclass. Loading errors are reported in the keep launcher and never crash the app.
- A theme only imports from `tagalot.themes.api`, the stable public surface. Everything else in `tagalot` is internal.
- **Loading** (`themes/loader.py`, `load_themes()`) returns a catalog of themes by id plus a list of problems, each tied to a file; it never raises. Order: built-in themes, then the user folder (`platformdirs.user_data_dir("tagalot", appauthor=False)/themes`, e.g. `%LOCALAPPDATA%\tagalot\themes`), then extra folders. Files and packages whose names start with `_` or `.` are ignored. Each file is imported under its own unique module name, so two themes can't collide and reloading replaces the old module; any exception while importing (including `SystemExit`) is reported with its line. A module with zero or several `Theme` subclasses is a problem, except that built-in modules without a theme are placeholders for themes still to come. For duplicate theme ids the first one found wins and later ones are reported, so a user theme can't silently replace a built-in.
- **Validation** without a database: name, positive version, an `api_version` this Tagalot provides, lowercase extensions starting with `.`, at least one entity, unique role names with at most one primary role per type, and containment, views (types, default sort fields, role/gallery/related sections), and actions referring only to what the theme declares; plus a trial table build (§5), so field and naming problems surface in the launcher too.

### What a theme declares

```python
from datetime import date
from tagalot.themes.api import (Theme, Entity, field, role, contains, related,
                                SearchView, DetailView, Section, action)

class Actor(Entity):
    title_label = "Name"           # relabels the core `entity.title` column
    born:    date | None = field("Date of birth", search="range")
    country: str | None  = field("Country", search="choice")
    roles = [role("photo", kinds={"image"}, many=False, thumbnail=True)]

class Collection(Entity):
    roles = [role("folder", kinds={"dir"}, primary=True)]

class Movie(Entity):
    year: int | None = field("Year", card=True, search="range")
    roles = [role("video", kinds={"video"}, many=True, primary=True),
             role("poster", kinds={"image"}, thumbnail=True),
             role("screenshot", kinds={"image"}, many=True)]

class MoviesTheme(Theme):
    id, name, version = "movies", "Movies", 1
    extensions = {".mkv", ".mp4", ".avi", ".jpg", ".png"}
    entities = [Actor, Collection, Movie]
    containment = [contains(Collection, Movie)]
    relationships = [related("cast", Actor, Movie, label="Filmography", reverse_label="Cast")]
    views = [
        SearchView("Movies", types=[Movie], inherit_tags=True, show_contained=False),
        SearchView("Actors", types=[Actor]),
        DetailView(Movie, sections=[Section.fields(), Section.role("poster"),
                                    Section.related("cast"), Section.gallery("screenshot")]),
    ]

    def prepare(self, batch): ...              # optional: read files in a worker (§6)
    def ingest(self, batch, ctx): ...          # resources -> entities, links, fields (via ctx)
    def thumbnail_chain(self, entity_type): ...  # ordered providers (§10)
    def similarity(self, a, b) -> float | None: ...  # optional, for dedupe (§13)
    def migrate(self, from_version, ctx): ...      # theme schema upgrades
```

(Exact names are illustrative; the implementation should keep this shape.)

**The API module** (`tagalot/themes/api.py`, `API_VERSION = 2`; version 2 added `migrate_schema`) imports only the standard library, so the core and the launcher can import it without side effects. Beyond the names above it provides:

- `Theme` class attributes: `id`, `name`, `version` (the theme's schema version), `api_version`, `extensions` (lowercase with the dot; empty = all), `dirs` (whether folders become resources: `bool` or a predicate on the relative path), `entities`, `containment`, `relationships`, `views`, `options` (a list of `option(name, default, *, label, description)`; the type is the default's: bool, int, float, or str; set per keep and root in `keep.toml`, §4), `thumbnail_max` (default 256) and `thumbnail_default` (default 128) (§10 "Sizes"); methods `prepare(batch)` (optional file reading in a worker, returning `{resource id: value}`, §6), `ingest(batch, ctx)`, `migrate_schema(from_version, ops)` (renaming, retyping, and dropping fields; see "Theme schema versions"), and `migrate(from_version, ctx)`; `type_id_of`, `table_name_of`, and `actions()` for the core.
- `Entity` class attributes: `label` and `plural` (how the type is named in the UI: "Album" / "Albums"; defaults are the class name and a regular English plural, `+es` after s/x/z/ch/sh and `y`→`ies` after a consonant, so irregular words such as "Series" or "Person" set `plural`; `entity_label(cls)` / `entity_plural(cls)` / `plural_of(word)` compute them), `title_label`, `roles`, `double_click` (`"page"` or `"open_file"`), `card_lines` (field names shown under the title on grid cards, default none; §12), `contents_sort` (for a container, the `SortBy` keys ordering what it holds in the tree layout and on its page, naming fields of the types it can contain; items without the field sort first; default by title; the loader refuses unknown fields), and optional `table_name` / `type_id` overrides. `entity_fields(cls)` resolves annotated fields (types `str`, `int`, `float`, `bool`, `date`, `datetime`, each optionally `| None`) in declaration order.
- `Kind` (the resource kinds a role accepts: image, audio, video, font, archive, dir, any), with `KIND_EXTENSIONS` and `kind_of(resource)` classifying resources by extension; `SortBy(field, descending)` for view defaults, and `Section.contents()` / `Section.custom(factory)` alongside the sections shown.
- `@action(label, applies_to)` marks a theme method called as `method(entities, ctx)`; `applies_to` lists entity types or role names.
- Values themes receive: `EntityRef(id, type)`, `Record(ref, title, fields, extra)`, `ResourceInfo(id, root_id, relpath, kind, ext, size, mtime_ns, path)`, and the `IngestContext` protocol (below).
- Thumbnails (§10): `Theme.thumbnail_chain(entity_type)` (default `default_thumbnail_chain`), the `ThumbnailProvider` base class, the built-in providers, and the read-only `ThumbnailContext` providers receive.
- Obvious mistakes (an unknown `search` kind or role kind, an unsupported field type, a missing annotation) raise `ThemeDeclarationError` at declaration; whole-theme checks happen in the loader.

Theme modules do not import SQLAlchemy. Entity classes are plain declarations; table names (`movies_actor`) and type ids (`movies.actor`) are derived from the theme id and the lowercased class name, overridable with `table_name` / `type_id` class attributes.

### Mapping and isolation

Importing a theme module never touches a database or a SQLAlchemy registry. This keeps themes isolated from each other and from the app:

- **At startup (launcher):** every theme module is imported and its declarations are validated without a database: unique theme id, valid field types and `search` kinds, at most one primary role per type, containment and relationships referencing declared types, views referencing declared roles and relationships. Problems are shown in the launcher next to the theme and never crash the app. The launcher also compares the theme version with each keep's `keep.toml`.
- **When a keep opens:** the core builds a fresh `MetaData` holding the theme's entity tables and relationship link tables as SQLAlchemy Core `Table` objects (each entity table's `id` references the core `entity.id` column directly), then creates or migrates them. Errors at this stage (for example, a table that cannot be built) are reported for that keep only; other keeps and themes are unaffected.
- **Consequences:** a broken theme affects only keeps that use it; a theme can be reloaded without restarting the app (useful while developing one); each test builds a clean schema. Because themes never hold SQLAlchemy objects, a SQLAlchemy upgrade cannot break a third-party theme.
- **Choosing and reloading** (`core/theme_db.py`): `resolve_theme(catalog, keep)` returns the keep's theme or explains why it isn't available (not installed, or its file had problems, listed with paths). `reload_theme()` re-imports user theme files, resolves the theme again, and reopens it: added types and fields take effect at once, a version bump asks to migrate as on open, and a broken edit raises without changing anything, so the previous schema stays in use. Built-in themes ship with the app and are not reloaded.

### Fields

Every entity has the core `title` column (display name, always text-searchable, shown on cards). A theme relabels it with `title_label` rather than defining its own name column.

Fields are declared as annotated class attributes: `name: <type> = field(label, *, card=False, search=None, editable=True, detail=True, display=None)`. `display` formats a number field for people (#184): `"bytes"` shows a size as `3.0 MB` (1 KB = 1024 bytes, up to TB), `"duration"` shows seconds as `3:25` or `1:02:03`; `DISPLAY_FORMATS` lists them and the loader refuses a format on a field that isn't an int or float. `"url"` on a `str` field (#298, API version 3) shows a web address as a link on the item's page, opening in the browser (`QDesktopServices`; Tagalot never fetches it), only for `http` and `https` addresses (anything else shows as plain text, `core.formats.is_web_address`); in lists, cards, and chips it reads as the address, since a click there selects the item. The loader refuses `"url"` on a field that isn't `str`, and `"bytes"`/`"duration"` on one that isn't a number. Field values on pages are always plain text otherwise, never markup. The number formats apply wherever values are shown (list cells, card lines, detail pages, the preview strip, filter chips and choices, `core/formats.py`); sorting, filtering, and editing use the stored number. Supported types are `str`, `int`, `float`, `bool`, `date`, and `datetime`; `X | None` makes the column nullable. `field()` returns a plain field spec; the core turns it into a typed column when the keep opens. `search` is one of `"text"`, `"range"` (numbers/dates), `"choice"` (distinct values), or `None`. The core generates cards, detail sections, edit forms, and filter widgets from this metadata. Every entity also has the JSON `extra` column for ad-hoc user fields (searchable by text only).

### Roles

`role(name, *, kinds, many=False, primary=False, thumbnail=False, label=None)`:

- `kinds`: accepted resource kinds (`image`, `audio`, `video`, `font`, `archive`, `dir`, `any`). Drag-and-drop onto a role slot rejects other kinds.
- `many`: one or many resources.
- `primary`: the entity's main content; defines "open file" (§11). At most one primary role per type.
- `thumbnail`: this role is tried early in thumbnail resolution.
- `gallery` and `folders` (planned, M28, API version 8): a picture role shown as a gallery, which the core fills from the named subfolders of the item's folder and archives of those names (§9 *Galleries*).

### Containment and relationships

- `contains(Parent, Child)` declares containment. The ingester creates edges via `ctx.contain(parent, child)`; the core maintains the closure table.
- `related(name, A, B, *, label=None, reverse_label=None, many=True, ordered=False)` declares a non-containment relationship (Actor ↔ Movie cast). `label` titles the section on an A's page (an actor's Filmography), `reverse_label` the one on a B's page (a movie's Cast). The core builds a link table `(a_id, b_id)`; `many=False` limits each `B` to at most one `A`. The ingester creates links via `ctx.relate(name, a, b)`. `DetailView` sections reference relationships by name, from either side.
- **Containers made by hand** (#329, API version 4; chosen in review over a relationship): an entity type with `made_by_hand = True` (the research theme's Project) is one the user makes and fills. Its views get **New <type>…** in their header (asks a name, makes the item, an item without an ingest key that scans never delete, and opens its page); items of the types it can contain (its declared containment) get **Add to <type>…** on their right-click menus (for the selection: choose one, or name a new one, in the Add dialog); and its page's contents list gets **Remove from <title>**. Each is one undo step (`core/containers.py`); what the user put in or took out is recorded in `user_contains`, so scans never undo it. Being ordinary containment, a project's tags count for its papers with inherit tags, and "Within" a project lists its papers.
- **A type with itself** (#322, API version 4): `related("cites", Paper, Paper, label="Cites", reverse_label="Cited by")` has a direction: an item's page shows two related sections, its `a` side under `label` and its `b` side under `reverse_label`, each an embedded search of its side only (`SearchSpec.related_side`, `"a"` or `"b"`, saved in the spec's JSON as the related object's `side`), with its own **Add…** (adding to "Cited by" makes the other item cite this one) and **Remove**; an item can't be related to itself, and Add… offers the item as already there. `symmetric=True` (only for a type with itself) has no direction: one section lists the items related either way ("Related").
- **Ordered relationships** (#317, API version 4): `ordered=True` (which needs `many=True`) keeps each `B`'s `A` items in an order, such as a paper's authors. The link table gains a nullable `position` (added to an existing keep's table by the additive sync); items without one sort after the rest. `ctx.relate(name, a, b, position=n)` places `a` among `b`'s items (0 first; gaps are fine); without a position a new item goes last and an existing one stays. A position on an unordered relationship is an `IngestError`. `ctx.related(name, b)` returns `b`'s items in order (an `A`'s side stays in id order). A `B`'s page lists them in order: its related section's list, and its embedded search, which sorts by the special key `@position` (`core.search.POSITION`, valid only in a related search of an ordered relationship). By hand: **Add…** puts the new item last, and **Move up** / **Move down** on the items' menus (several at once, keeping their order among themselves, stopping at the ends; one undo step, `core.relations.move_related`) record a `user_order` row, after which scans keep that order (new items from files go last; removals still follow #260). Merging: an `A` merged into another keeps its place on each `B`; a merged `B`'s items go after the kept `B`'s, and its `user_order` comes along.

### Ingest context

Themes read and write keep data only through the context object `ctx` passed to `ingest()` (and to actions and `migrate()`). Entities are referred to by opaque `EntityRef` handles, not ORM objects. The core applies all writes through the DB writer (§6) and enforces provenance: extracted values never overwrite fields whose provenance is `user`.

- `ctx.upsert(Type, key, *, title=None, **fields) -> EntityRef`: find the entity of that type with this `ingest_key` (§5) or create it, then set extracted fields. An item the user merged into another (§13, `entity_merge`) isn't created again: the ref stands for the merged item, and links, edges, relations, updates, and deletes given for it are dropped (`get` reads the item it went into). Likewise `ctx.entities_of(file)` includes a merged item that had the file from its theme (`entity_merge_resource`), so a theme that finds items through their files doesn't make a new one. The key is the theme's stable natural key (for example, an album's folder path or a normalized artist name).
- `ctx.link(entity, resource, role, sort_order=0)`, `ctx.unlink(...)`. Links the user made by hand (`by_user`, #243) are the user's: `unlink` never removes them, and in a one-file role a theme's `link` is skipped while the user's file is there (removing the user's link lets the theme's come back at the next re-read).
- `ctx.contain(parent, child)`, `ctx.uncontain(parent, child)`. Within a batch the last call for an edge wins, so a theme may contain and later uncontain (or the reverse) as it works things out.
- `ctx.relate(name, a, b)`, `ctx.unrelate(name, a, b)` (the user's hand edits win, #260: `unrelate` leaves a relationship the user added, `relate` doesn't restore one the user removed, and in a `many=False` relationship it doesn't displace the user's partner), and `ctx.related(name, entity) -> list[EntityRef]` (the entities on the other side, from either end, in id order; #258), so a theme can see what it related before and let go of what's gone.
- `ctx.find(Type, **equals) -> list[EntityRef]` and `ctx.get(entity) -> Record` (read-only field values) for lookups.
- `ctx.keywords(entity, resource, keywords)` (#294; additive, so `API_VERSION` stays 2): the keywords one file gives an item (§7 *File keywords*), replacing what that file gave before (an empty list clears them; unlinking the file from the item clears them too); they become tags only by matching defined tags.
- `ctx.option(name)`: an option's value for the root being scanned (its override, else the keep's, else the default); `ctx.contents(entity)` (direct children, counting this batch's pending `contain`/`uncontain`) and `ctx.linked(entity, role=None)` (linked resource ids); `ctx.delete(entity)` deletes an entity the theme made (its links, containment, and tags go with it; resources stay), for example an artist left empty. In a scan, an item the user made by hand (no ingest key, such as an actor added to a cast as new, #260) is left alone.
- `ctx.prepared(resource)`: what `prepare()` returned for the resource, or `None` (nothing returned for it, or no prepare step, as in `migrate` and actions).
- `Theme.read_last` (#320, API version 4): extensions of files that describe other files (a bibliography export): a scan ingests them after its other pending files, and when it ingested others in that root, ingests every such file of the root again (`scanjob._read_last`). As a tuple, its extensions are read in that order (#321: bibliographies, then the notes that use their citation keys); as a set, by path.
- `ctx.resource_at(beside, relpath)` (#297; `API_VERSION` 3, decided in review): the file or folder at a root-relative path in the same root as `beside`, as a `ResourceInfo` with this computer's path (made from `beside`'s), or `None` if it isn't scanned (not among the theme's extensions, skipped, or known missing). Case is ignored when nothing matches exactly. Resources are all recorded before any is ingested, so it finds a file whether or not that file has been ingested yet. It is how one file links another it names, such as a Markdown book's cover picture.
- `ctx.update(entity, title=None, **fields)`: set extracted values on a known entity, with the same provenance rules as `upsert`.
- `ctx.entities_of(resource, role=None) -> list[EntityRef]`: the entities linked to a resource. Because move detection (§6) carries links to a file's new path, this is how a file-based theme finds "the entity for this file"; keying such entities by path would let a new file at a vacated path take over a moved file's entity. Links the user made by hand aren't returned: the file isn't the theme's to read into that item, so re-reading it never renames or regroups the user's item (the theme may make an item of its own for it). `ctx.linked(entity)` does count them, so an item with only the user's files isn't "empty".
- `ctx.warn(resource, message)`: report a problem with a file to the activity panel.
- `ctx.note(entity, folder)` (#379, API version 8): the note inside `folder` (a folder resource) is the item's (§9 *Notes*); recorded in `entity_note.folder_id`, so later scans keep looking there. Naming another folder reads its note afresh.
- Actions get an `ActionContext`, a superset of this one; see Actions below.

Batch items are read-only `ResourceInfo` values: root id, relative path, kind, extension, size, mtime, and a readable local path. Themes may open files for reading; they must never write under a root.

Implementation details (`core/ingest.py`, `IngestSession`):

- **Provenance:** `upsert` records `extracted` provenance for the title and every field it writes, and skips any the user edited (`user`), title included; the entity is still found by its ingest key after the user renames it.
- **Validation:** an unknown field, a role not declared on that type, undeclared containment, a relationship between the wrong types, or a type from another theme raises `IngestError` (a theme bug; the pipeline reports it per batch).
- **Single-valued roles** (`many=False`) keep one resource: linking another replaces it. Relinking updates `sort_order`. Likewise a `many=False` relationship keeps one `a` per `b`.
- **Batching:** containment edges and search-index updates are collected and applied by `flush()` (`closure.apply`, whose rejected edges become warnings, then `fts.sync_entities` with the theme's `search="text"` fields). The pipeline calls `flush()` before each transaction commits.
- `ctx.warn()` collects warnings (root, relative path, message) for the activity panel.

### Views

- `SearchView(name, types, *, inherit_tags=False, show_contained=False, aggregate_up=False, layout="grid"|"list"|"tree", default_sort=...)`.
- `DetailView(type, sections=[...])` with sections for fields, role slots, galleries, related entities, and, for containers, an **embedded search** of contents.
- Escape hatch: a view or section may return a custom `QWidget` factory. The core passes it a limited context object (selection, navigation, open-entity callbacks).
- `double_click` per type: `"page"` (default) or `"open_file"`; the other action moves to Ctrl+Enter.

### Actions

`@action(label, applies_to=[types or roles])` registers a context-menu and detail-page action, for example "Play album" (write a temporary `.m3u` in track order and open it with the OS). Actions must not modify user files.

Implementation (#106, `core/actions.py`, `core/entity_state.py`):

- **Applies to** an entity type listed, or a type that declares a role listed. `actions_for(schema, type_id)` lists them in declaration order.
- **Called as** `method(entities, ctx)`. `entities` are the selected items the action applies to (the clicked item if it isn't selected), or the page's item. `ctx` is an `ActionContext`: everything the ingest context offers (its writes keep the same provenance rules), plus `contents(entity)` in the container's `contents_sort` order, `resources(entity, role=None)` (files with this computer's paths, leaving out missing and offline ones), `temp_path(name)` (a file in a folder of the session's own, deleted when the keep closes; only the name's last part is used), and `open(path)`, `reveal(path)`, `message(text)`; and, in API version 4 (#322), `copy_text(text)` (the clipboard), `open_url(url)` (`http`/`https` only, in the browser; anything else is an `ActionError`), and `save_text(name, text)` (a file name without folders: after the action, a save dialog starting in the last folder chosen; see §4 *Saving an export*). Outputs are carried out in order after the commit.
- **Runs in the DB writer**, in one transaction: an exception rolls back everything it wrote, and the status bar says "<label> failed: …". Outputs are collected and carried out on the GUI thread after the commit, in order. `open` honors the user's overrides (§11). The status bar shows the action's last message, else "<label>: done."
- **Undo:** while an action runs, the ingest session tells a `ChangeRecorder` about every entity before its first write. That covers both ends of a containment edge or relationship, a deleted entity's neighbours, and a many=False relationship's previous partner. A created entity is recorded as not existing. Each is snapshotted whole: row, theme fields, provenance, file links, tags, parents and children, and relationships. Snapshots are taken again at the end. The run is one undo step (`ActionChange`, labelled with the action), recorded only if something changed. Undo and redo restore the snapshots exactly: created entities are deleted, deleted ones are recreated with their id, tags, and edges, and the closure and search index are brought up to date. `updated_at` and the thumbnail memo are not restored; they are set afresh.
- **Where:** a result's right-click menu lists the actions for its type, after Re-read. A detail page shows them as buttons beside More ▾. Contents searches on a page get the same menus.

### Online details (M22, #307; designed in review, core in #339)

Looking items' details up online by identifier: Research papers by DOI (Crossref) and arXiv ID (arXiv), Books by ISBN (Open Library). It is the first time Tagalot uses the network, so it is narrow on purpose (decided in review, 2026-10-05):

- **Only the core goes online** (chosen over themes fetching for themselves). A theme declares the services it uses, `online_sources = [OnlineSource("Crossref", "api.crossref.org", "DOIs")]` (a name, a host, and what is sent), and two methods: `online_requests(entity_type, item)` gives the addresses to fetch for an item (only `https` addresses on its declared hosts; others are refused), and `online_details(entity, responses, ctx)` turns the responses into the item's details in the DB writer. So the consent dialog can name every service and what it is sent, and nothing else leaves the computer. Theme API version 5 (version 4 shipped in 0.7.0).
- **Fetching** (`core/online.py`): the standard library's `urllib` (no new dependency), `https` only, a `User-Agent` naming Tagalot and its version, a timeout, at most one request a second to each host (three seconds for arXiv, as it asks), and backing off on `429` and server errors. Offline, or when a service fails, nothing changes and the items are tried again later. Responses are cached in the keep (a core table, keyed by address, with when it was fetched), so an identifier is fetched once; **Look up online** fetches again.
- **Consent, per keep:** nothing is looked up until the first time a lookup would happen. Then Tagalot asks once, naming the services the theme declares and what each is sent ("Look up details online? Tagalot would send DOIs to Crossref and arXiv IDs to arXiv. Nothing else about your files leaves this computer."), with **Allow for this keep**, **Not now** (ask again next time; nothing is sent), and **Never**. The answer is saved in `keep.toml` (`[online] lookups = "allow"` or `"never"`) and can be changed in Keep configuration (Keep tab). With **Never**, **Look up online** offers to turn lookups on.
- **When** (chosen in review): automatically, in the background after a scan, for items the scan made or changed whose identifiers have no cached response; and on demand, **Look up online** on selected items (or a page's More menu), which refreshes. Progress shows in the status bar and the activity panel; problems (a service down, an identifier it doesn't know) are listed there.
- **What wins** (chosen in review): looked-up details rank **below the files' own curated metadata** and above what Tagalot guesses from a file. In the research theme: a literature note, then a sidecar, then a library export, then online details, then the PDF, then the file name; the user's edits always win (fields written from online details have provenance `fetched`, §5). A theme without ranked sources fills in only fields that are empty.
- **Privacy:** only the identifiers in the addresses are sent; no account, key, or telemetry. The addresses fetched are logged.
- **As built** (#339): `OnlineSource(name, host, sends, interval=1.0)` checks the host is a bare lowercase host name; a theme with `online_sources` needs `api_version = 5`, and names each host once. Addresses must be plain `https` on a declared host (no other port, no user name); anything else is reported in the activity panel and never fetched. A redirect is followed only to `https` on the same host (Open Library sends `/isbn/…` to `/books/…`); one elsewhere is treated as an answer, never requested (#340). `online_details(entity, responses, ctx)` runs once every address `online_requests` gave has an answer: `responses` maps each address to an `OnlineResponse` (`url`, `status`, `text`, `ok`, `json()`); an item with a kept answer for every address is applied again from the keep, without going online. A service is waited for 20 s; a busy one (`429` or `5xx`) is tried twice more, after its `Retry-After` or 5 then 10 s (never more than a minute); one that can't be reached or stays busy is given up on for the rest of that run, and its items are left for next time (other services go ahead). The theme's `ctx` is an ingest context whose values are marked `fetched`; reading a file again (extraction) replaces `fetched` values like any extracted ones, so a file's own details win unless the theme ranks its sources. An item the theme fails on is rolled back alone and reported. Lookups aren't undo steps, like scans: the user's edits are never touched. `KeepSession.look_up` refuses unless `keep.toml` says `lookups = "allow"`; the Keep tab has **Look up details online**, shown for themes with services.
- **In the window** (#340, `ui/lookups.py`): after each scan, the items it made or changed (created or updated since it began) are looked up; those with kept answers for every address are applied again from them, without going online. The question is asked only when a lookup would fetch something, so a keep whose theme finds no identifiers is never asked. **Allow for this keep** (or turning lookups on in the Keep tab) then looks up every item without kept answers, once, so what was already in the keep isn't left out. **Not now** isn't asked again until the keep is opened again, except by **Look up online**. **Look up online** is on every item's right-click menu (for the selection) and its page's More menu in a theme with services, whatever the type: the theme decides what each item has to look up, and "Nothing to look up online" says when nothing did. With **Never**, it offers to turn lookups on. One run at a time; requests made meanwhile wait their turn. The status bar shows "Looking up online: N left", then a summary ("Looked up 12 items online, 2 not found."); problems go to the activity panel. Closing the keep stops a run before its next request.
- Movies (TMDb, which needs an API key) and music (MusicBrainz) can follow on the same hooks.

### Notes (M27; designed in review, 2026-10-10)

A **note** is a Markdown file that describes an item: its front matter gives details and tags, its body is shown on the item's page. Notes let the user say what no file says: a friendlier name for a collection's folder, an artist's background, facts about an actor. Tagalot reads notes and never changes them, except **Save as note…** into a notes folder the user made writable (below).

- **Where notes come from:**
  - **Folder notes:** an item whose primary file is a folder (assets' Artist, music's Album, movies' Collection) takes the note inside that folder: `<folder name>.md`, else `index.md`, else `README.md`, each also as `.markdown`, names compared ignoring case. When several are there, the first in that order is the note; the others stay ordinary files. Only inside the folder: a note beside it (`Parent/Folder.md`) isn't looked for.
  - **Notes a theme names:** `ctx.note(entity, folder)` (API version 8) applies the note inside `folder` (a folder resource, found by the same names) to an item whose primary file isn't a folder, such as a Movie and its folder. The core does the reading, so every theme's notes behave alike.
  - **The notes folder:** one folder per keep, chosen in Keep configuration, for items that have no folder (actors, authors, series, a music artist). See *The notes folder* below.
  - **In-app notes:** an item without a note file can have a note typed on its page, stored in the keep (below).
- **One note per item.** A folder note (or one a theme names) wins over a notes-folder note for the same item; Triage lists the other as a second note.
- **Scanning:** the scanner records Markdown files named as notes (`<folder name>.md`, `index.md`, `README.md`, and `.markdown`) in the folders the theme records (its `dirs` rule), whatever the theme's extensions, so notes are found in themes that don't take `.md` (assets, music, movies). (As built, #379: only those folders, not every folder, so a `README.md` elsewhere is neither recorded nor listed as unlinked.) A note-named file the theme doesn't take, and a file that is an item's note, is never handed to the theme as content; an item's note isn't listed as unlinked (a second note in the same folder is). A note that changes is read again at the next scan, and its item updated.
- **What a note gives** (`core/notes.py`), from its front matter (YAML or TOML, as `read_front_matter` reads it) and body:
  - **Title** (`title`): the item's title. For a folder note it wins over the title the theme took from the folder's name (the only other source); for other notes it fills an empty title, as a field does. The user's edit always wins.
  - **Tags** (`tags`, `keywords`): file keywords of the item from the note file (§7 *File keywords*): they become tags only by matching tags the user defined, and unmatched ones are listed in Triage like any file's.
  - **Fields:** a key matching one of the type's fields, by its name or its label (ignoring case, spaces, `_` and `-`), sets that field, converted to its type (a value that doesn't convert is reported in the activity panel and skipped). A note ranks **below the theme's own reading of files** (an `.nfo`, embedded tags, an EPUB's package) and **above online details**: it fills a field that no file gave, replaces a value looked up online, and gives way when a file later gives the field. The user's edits win over all of them. Values from a note have provenance `note` (§5): a note that changes updates them; a note that drops a key clears the field it set.
  - **Everything else** becomes an **Extra field** (§12) with provenance `note`: lists are joined with `, `, dates written as `YYYY-MM-DD`, nested tables skipped. Deleting one on the item's page is remembered for that item (`note_key_removal`, one undo step), so later scans leave it off; editing one makes it the user's (provenance `user`), and scans no longer change it. A key the note no longer has is removed, unless the user edited it.
  - **Body:** the Markdown after the front matter (without a leading `# Title` heading that repeats the title), shown in the page's header (§12) and searchable as text (`entity_fts` body).
- **As built** (#379, `core/notes.py`):
  - **The notes step:** after a root's files are ingested, the scan finds the root's items that take notes (`note_sites`: those whose primary role is a folder, and those with an `entity_note.folder_id`), each folder's best-named note (`note_files`; a `.md` before a `.markdown` of the same name), and reads only those whose file, size, or time differ from `entity_note` (`read_notes`, in the scan's thread, never the DB writer's); one writer job applies them (`apply_notes`). The status bar says "Looking for notes in …". A note that can't be read (unreadable, front matter that doesn't parse) is reported in the activity panel and the item keeps what its note gave before; a value that doesn't convert is reported and left out.
  - **A value the note stops giving** (the note changed, or its file is gone) is cleared, its provenance dropped, and the item's primary files are marked pending and ingested again at once, so the theme's own value (the folder's name, a file's field) comes back.
  - **Files and a note's values** (`IngestSession._apply_extracted`): themes write every field each time they read a file, empty ones included, so a file's empty value never replaces a note's, a folder note's title is never replaced by the folder's name, and online details (`fetched`) never replace a note's value. A file's non-empty value does replace a note's (the theme's own reading ranks above the note).
  - **Missing isn't gone:** only items whose folder is there (`ok`) are looked at, so a folder or note found missing keeps the note it had (AGENTS.md rule 7); a deleted resource sets `resource_id` null and the note goes at the next scan.
  - **Snapshots** carry an item's `entity_note` row and its `note_key_removal` keys, so undoing a merge or an action brings them back.
  - **On the page** (#380, `core/note_markdown.py`, `ui/note_view.py`): the body is rendered with Qt's Markdown (`QTextBrowser.setMarkdown`), after Obsidian's `![[picture.png]]` embeds become Markdown pictures and `[[Note|shown]]` links their text (`renderable`). The document loads nothing itself (`loadResource` answers only from what was read), so the GUI thread never reads a disk or a share: the page's worker reads the note's pictures from its folder (`read_pictures`: relative paths only, at most 12, 10 MB each, picture extensions only; web pictures aren't fetched) and scales them to at most 480 px wide. Links open web addresses in the browser and relative paths (resolved from the note's folder, `resolve_link`; absolute paths and other schemes are ignored) with their program. **Open note** opens the note file through the usual file opener (`resource_to_open` finds a note file, which no role links). The cap is the thumbnail's 192 px less the breadcrumbs, title, and type above the note, at least about three lines.
- **Keys Tagalot reads itself** start with `tagalot-` (`tagalot-type`, below), are never Extra fields, and can't be ignored. `aliases` is read, not shown: a notes-folder note matches an item by them.
- **Ignored keys** never become Extra fields. Three lists apply together: built-in defaults for housekeeping that editors add (`cssclasses`, `cssclass`, `publish`, `permalink`, `position`); the user's own, in `settings.toml` (`[notes] ignore_keys`, for every keep on this computer); and the keep's, in `keep.toml` (`[notes] ignore_keys`, travelling with the keep). An Extra field from a note has **Ignore this key in every note…** (for this keep), and Keep configuration lists both editable lists. Ignoring a key removes its Extra fields from the keep's items (undoable).

#### The notes folder

- **Choosing it** (Keep configuration, Folders): any folder inside a watched folder (`Assets/Notes`), or a folder of its own, which is then added as a root used only for notes. Tagalot never recognizes a notes folder by its name (a music library may have an album called "Notes"). `keep.toml`: `[notes] root = "<root id>"`, `path = "Notes"` (inside that root; empty for the whole root).
- **Not content:** nothing under the notes folder is handed to the theme, as if it were on the root's Skip list; Tagalot reads it only for notes and their galleries (*Galleries*, below).
- **Which type a note is for:** its `tagalot-type` key (a type's name or label, singular or plural, ignoring case: `actor`, `Actors`), else its subfolder's name the same way (`Notes/Actors/Keanu Reeves.md`), else any type. The key wins when both are there, so a note in the wrong folder can be corrected from inside it. Notes may sit in one folder with `tagalot-type`, in a subfolder per type, or both.
- **Which item:** the note's title (`title`, else its file name without the extension) or one of its `aliases` equals the item's title or one of its own aliases, ignoring case and accents. One item of the type matching is the note's item; a renamed item keeps its note through `aliases` (or Triage asks).
- **Triage** gains **Notes**: notes that match no item, notes matching several items (add `tagalot-type`, or an alias), and items with two notes; each with **Open note** and **Show in file manager**.

#### In-app notes and Save as note…

- **Typing a note in Tagalot:** every item's page has a **Notes** box (Markdown, shown rendered, edited in place like a field). It is stored in the keep (`entity_note` with no file), one undo step per edit, and searchable. An item with a note file shows that file's body here, read-only, with **Open note**: the file is where it's edited, and the keep holds only what it last read from it (re-read at scans, kept while the file is offline, removed with the file), so every item has one place its note is edited.
- **Save as note…** (an item's More menu, offered when the notes folder is writable and the item has no note file) writes the in-app note as a new file in the notes folder: front matter with `title`, `tagalot-type` (in the one-folder layout), and the item's tags (as Write to file… writes them, §4), then the body. The next scan reads it, and the item's note is the file's from then on.
  - **Writable on its own:** the notes folder is marked writable separately (`[notes] writable = true`, Keep configuration asks first), so a notes folder inside a content folder can be written without making that content folder writable. Nothing else is written, and nothing is ever replaced: an existing file of that name is reported, not overwritten. File names are made safe for every system (`:`, `?`, `*`, `/`, `\`, `"`, `<`, `>`, `|` replaced).
  - **Layout** (`[notes] new_notes`): `"folders"` (a subfolder per type, named by its plural: `Actors/Keanu Reeves.md`) or `"one-folder"` (all in the notes folder, typed by `tagalot-type`). Notes Tagalot didn't write may follow either.

### Galleries (M28; designed in review, 2026-10-10)

Pictures that belong to an item, browsed on its page: a movie's screenshots, an album's scanned booklet, an artist's previews, an actor's photos.

- **A gallery is a role** (`role(..., many=True, gallery=True)`, kinds `image` and `archive`), shown by `Section.gallery(name)` (§12). Besides the files a theme links to it, a gallery role can name **folders** (`folders=("Screenshots", "Screens")`, API version 8): the core fills it with the pictures and archives under those subfolders of the item's folder (its primary folder, else the folder of its primary file), at any depth, and with archives of those names beside them (`Screenshots.zip`, `.rar`, `.7z`). Names are compared ignoring case.
- **Notes-folder galleries:** a note in the notes folder may have a folder or archive of the same name beside it (`Notes/Actors/Keanu Reeves/`, `Keanu Reeves.zip`): its pictures and archives fill the item's first gallery role. This is how an item without a folder gets a gallery.
- **What a gallery shows** (level 1, chosen in review): loose pictures first, then one group per subfolder (headed by its name, `The Matrix`), then one group per archive (headed by its file name), each group's pictures in natural name order. An archive's pictures are listed when the page opens, in a worker, with the thumbnails' archive reader and its budgets (§10 *Archives*); its pictures aren't resources and can't be tagged or linked on their own. An archive inside an archive isn't opened (it shows as one picture, its best). Opening a picture from an archive extracts it to the system temp folder and opens that copy; the archive is never touched.
- **Thumbnails of pictures in archives** are cached by the archive's resource, the member's path inside it, and the archive's size and time, so a changed archive makes them again.
- **The built-in themes' galleries** (M28): a Movie's **Screenshots** (`Screenshots`, `Screens`, `Stills`); an Album's **Scans** (`Scans`, `Artwork`, `Covers`, `Booklet`); an assets Artist's **Previews** (`Previews`, `Preview`, `Samples`); and, from the notes folder, an Actor's and a music Artist's **Photos** and a Book's **Covers**.
- **Archive members as items** (level 2) is future work (§14).

### Dashboard cards

A theme adds cards to the dashboard (§12) in two ways (#114, `themes/api.py`, `core/dashboard.py`):

- **Declared**, in `Theme.dashboard`, computed by the core in SQL (fast; no theme code runs):
  - `stat(title, Type, field, how="sum")` gives one number over the type's items: `"sum"`, `"avg"`, `"min"`, `"max"`, or `"count"` (items with a value). It is shown in the field's display format: `stat("Total running time", Song, "duration")` reads `1:02:33`. Other numbers read `1,234`, or with one decimal.
  - `top_values(title, Type, field, limit=5)` gives the field's most common values with their counts, most first. A value links to Search all narrowed to the type, filtered by how the field is searched: a choice filter, an exact range for a range field, "starts with" for text. A field that isn't searchable shows its values without links.
  - The loader checks the type is declared, the field exists, and a sum, average, minimum, or maximum is over a number field.
- **Methods**, marked `@dashboard_card(title, description="")`, for anything the declared kinds can't express:
  - Called as `method(ctx)` with a read-only `DashboardContext`: `count(Type, **equals)`, `find(Type, **equals)`, `get(entity)`, and `stat(Type, field, how)`.
  - Returns `(label, value)` rows or a text.
  - They run in the dashboard's worker on every read, so they should be quick.
  - A method that raises shows the error on its card ("Couldn't work this out: …"), and the rest of the dashboard is unaffected.

Declared cards come first, then method cards in declaration order. A card's `description` is its tooltip. The built-in themes' cards:

- **music:** Total running time and Average song (from `duration`), Top genres, and Top years (albums).
- **assets2d:** Space used by images, Image types (by extension), and the method card **Biggest artists** (assets per artist).

### Theme schema versions

On opening a keep, the core compares the stored theme version with the loaded theme's version: equal → open; older stored → run `migrate()` after backing up `keep.db`; newer stored → refuse to open with a clear message.

Details (`core/theme_db.py`, `open_theme()`, run after the core schema is open):

- The theme version is kept in `keep.toml` (`[theme] version`) and in `schema_version` (`component` = theme id), like the core version (§5). A newer version in either is refused before anything changes; an older stored version raises the same "needs migration" error as the core (with `component` set to the theme id) so the launcher can ask. Once confirmed, `keep.db` is backed up (`keep.db.<theme>-v<old>-<timestamp>.bak`), and in one transaction `theme().migrate_schema(old_version, ops)` runs, the additive changes are applied, items of types whose fields were retyped or dropped are re-indexed for text search, `theme().migrate(old_version, ctx)` runs, and the version is recorded; `keep.toml` is updated afterwards. A failure rolls everything back, DDL included, and the backup is kept; a schema change that fails says so, naming the backup.
- **Additive changes are the core's job**, on every open: missing tables, columns, and indexes are created (new non-nullable columns use the defaults from §5, which `ALTER TABLE ADD COLUMN` requires). So a theme that only adds entity types or fields needs no migration code, and `Theme.migrate()` defaults to doing nothing; it exists for data changes. A field the theme stops declaring is left in place (harmless) unless the theme drops it.
- **Renaming, retyping, and dropping fields are explicit** (#173), in `Theme.migrate_schema(from_version, ops)`, so the core never guesses that a missing field was renamed. Themes still never see SQL: `ops` (`SchemaOps`, implemented by `core/theme_migrate.py`) checks each request against the theme's declarations and the keep's tables, then:
  - `rename_field(Entity, old, new)`: `new` must be declared and `old` not. `ALTER TABLE … RENAME COLUMN`; the old column's indexes are dropped, and the additive step makes the declared ones under their new names. Field provenance moves to the new name, so user edits stay protected. Saved searches that can show that type (scoped to it, or to every type) have their filters and sorts on `old` renamed.
  - `change_type(Entity, name, convert=None)`: to the declared type, by copy and swap: a new table, the rows copied with the field converted, the old table dropped, the new one renamed, and its indexes made again. The `id` foreign key to `entity.id` is kept. The default conversion takes only what clearly converts: numeric text and whole floats to `int`, numbers to and from text, yes/no words and 0/1 to `bool`, and ISO text to dates and UTC datetimes. Blank text becomes `None` (or the type's default for a non-nullable field). `convert` replaces it, receiving SQLite's stored value. A value that doesn't convert fails the upgrade with the item id and value.
  - `drop_field(Entity, name)`: `name` must no longer be declared. Copy and swap without the column, and its provenance rows are deleted. Saved searches still naming it report an unknown field when opened, as before.
  - Each skips silently what the keep doesn't have (a field it never had, a type whose table the additive step will create), so `if from_version < N:` blocks work for keeps any number of versions behind. A field renamed onto one the keep already has is an error.
  - A theme defining `migrate_schema` must set `api_version = 2` explicitly (a validation problem otherwise), so a Tagalot with API version 1 refuses it rather than open the keep and skip its schema changes. Themes needing API version 1 use the interim pattern: keep the old field declared, hidden, for one version, and copy it in `migrate()`. The theme guide (docs/THEMES.md, "Changing a theme people already use") shows each case.

### Built-in themes

1. **generic** — one entity per file, no containment. Reference implementation and fallback; lets the core be built and tested before any rich theme exists. A `File` entity is titled with the file name and has `extension` (choice), `folder` (text), `size` and `modified` (range); its primary `file` role accepts any kind, and double-click opens the file. Views: "Files" and "Recently modified" (list layout). Ingest updates the entity already linked to a file, or creates one with a never-reused key.
2. **assets2d** — Artist ⊃ Image, Font, Archive (#81). Asset kinds are **separate entity types**, so each has its own fields and views can be scoped by type:
   - **Image** (every image extension, PSD included): `width`, `height` (range) and `dimensions` ("1920 × 1080", its card line). **Font** (ttf, otf, woff, woff2): `family`, `style` (choice; card lines). **Archive** (zip, 7z, rar, cbz, cbr, cb7): `images` (how many images it holds). All three share `artist` (choice), `extension`, `folder`, `size`, and `modified`; the title is the file name, and double-click opens the file.
   - One entity per file with a never-reused key, as in the generic theme, so tags follow a moved file. The **artist** is the folder at the `artist_level` option under the root (default 1, the first folder; a keep or a root can set 2 for `Store/<Artist>/…`); files above that level have no artist. Every folder is a resource (`dirs = True`), and ingest links only those at the level as artists' folders, so a changed level needs no rescan of the file system. After a level change the root is ingested again: assets move to their new artists, folders no longer at the level stop being artists' folders, and an artist left with no assets and no folder is deleted (its tags with it). Artists are keyed by folder name (case-insensitive), so the same artist's folders in two roots are one artist. Artists' folders are their primary `folder` role. A file moved to another artist's folder moves to that artist.
   - File details are read in `prepare()` with Pillow (the image header only; the font's names), `zipfile`, `py7zr`, and `rarfile` (the listing, not the contents). A file whose details can't be read is still an asset, with a warning.
   - Thumbnails: images and archives as usual; fonts by the core's **font renderer**, which draws "Aa" and "Quick fox" in the font; artists by their `folder.jpg` (`FolderImage`), else one of their first five assets (a theme provider, `ContentsThumbnail`). `thumbnail_max` 1024, `thumbnail_default` 256.
   - Views (#83), all grids: **Assets** (all three types), **Artists**, **Images**, **Fonts** (sorted by family, then style), and **Archives**. The asset views turn on `inherit_tags`, so a tag on an artist counts as its assets' own: tagging a whole artist "Pixel art" is one step, and Images with Pixel art lists that artist's images.
3. **music** — Artist ⊃ Album ⊃ Song, and Artist ⊃ Song (#98, #99).
   - **Albums are folders:** a folder with audio in it (directly, or in disc subfolders) is an album, keyed by its path and linked as its primary `folder` role. Folders named `CD1`, `Disc 2`, `Disk-3` belong to their parent's album and give their songs a disc number when the tags have none. An album is titled from its songs' `ALBUM` tag, else its folder name, and takes `year` and `genre` from them; `artist` and `folder` are not editable.
   - **Songs** are keyed by album folder, disc, track, and title (case and punctuation ignored), so `01 So What.flac` and `01 So What.mp3` are one song whose files are its versions (role `audio`, many). A song already linked to a file is updated in place, so tags and moves follow it. Fields: `track`, `disc`, `artist`, `album_artist`, `album`, `year`, `genre`, `duration` (seconds, shown as `3:25`), `bitrate` (kbps, the best of its versions; theme version 2, #253), `folder`. Double-click opens the file.
   - **Artists:** an album's artist is its songs' `ALBUMARTIST` tag, else their `ARTIST`, worked out again from all its songs whenever one changes; when they disagree (a compilation) it is **Various Artists**. A song by someone other than its album's artist also sits under its own artist, and a song with no album folder (directly in a root) under its artist only. Artists are keyed by normalized name. An album or artist left with nothing inside is deleted.
   - Thumbnails (#100): a **song** shows its embedded art, else its album's thumbnail (`AlbumThumbnail`, only the album parent, not an artist it also sits under), else the audio icon; an **album** its folder image (`folder.jpg`, `cover.jpg`…, in the album folder itself, not a disc folder), else its first songs' embedded art, else the folder icon; an **artist** the thumbnail of one of its first five albums or songs (`ContentsThumbnail`), else the generic icon.
   - Views (#101): **Browse** (albums and songs, Inherit tags and Contained on, starting as a tree sorted by artist, year, title: albums at the top with their songs under them), **Artists** (grid), **Albums** (grid, by artist, year, title), and **Songs** (list, by artist, album, disc, track, title); the album and song views inherit tags, so tagging an album tags its songs for searches. An album orders its songs by disc, track, then title (`contents_sort`), in the tree and on its page; an artist its albums and songs by year, then title.
   - **Opening** (#102): double-click or Enter on a song plays its first version that's on this computer (`double_click = "open_file"`); Ctrl+Enter opens its page. **Play album** (an action on albums: a page button and a menu entry) writes the selected albums' songs in disc and track order to an extended `.m3u8` playlist (UTF-8, `#EXTINF` with length and "artist - title") in the session's temp folder, named after the album (or "N albums"), with a new name if one exists (a player may still hold the last one), and opens it with the program for playlists. Songs with no file on this computer are left out, and the status bar says how many; with none, nothing opens. It changes no data, so there's nothing to undo.
   - **Genres as file keywords** (theme version 3, #295): every genre a song's tags give (several values, or one naming several: `Pop/Rock`, `Jazz; Blues`) is reported with `ctx.keywords`, so it can become the user's tag (§7 *File keywords*); the Genre field is unchanged.
   - Tags are read in `prepare()` with mutagen's easy tags; a file without tags is named from its file name (`01 - So What.mp3`: track 1, "So What"; `1-03 Blue.mp3`: disc 1, track 3) and its folder, and one mutagen can't read is still a song, with a warning.
4. **movies** — Collection ⊃ Movie, Actor ↔ Movie (#123).
   - **Movies from names:** a video's name gives the title and year (`Inception (2010)`, `Blade Runner [1982]`, scene style `The.Matrix.1999.1080p.BluRay`). Names that differ only in a part, quality, or edition suffix (`- 720p`, `cd2`, `part1`, `- Extended`) are one movie: videos side by side whose names match are its files (role `video`, many: versions or parts). Keys: `movie:<folder>|<title>|<year>`, ignoring case and punctuation.
   - **A movie's folder:** a folder named like a movie (`Inception (2010)/`), or whose videos are all one movie, is that movie's; its name gives the title and year when it has one, and every video in it is one of the movie's files (key `movie:dir:<folder>`). A folder of several different videos isn't one (`Home Movies/`: a movie per video). The root is never a movie's folder.
   - **Extras** aren't movies: names ending `-trailer`, `-sample`, `-featurette`, `-behindthescenes`, `-deleted`, `-interview`, `-scene`, `-short`, `-other`, a file named `sample`, and videos in folders named Extras, Featurettes, Behind The Scenes, Deleted Scenes, Interviews, Scenes, Shorts, Trailers, Other, or Samples (Plex's names). They're left unlinked (Triage lists them; Skip in scans hides them).
   - **Collections:** a folder below the root holding two or more movies' folders is a collection (key `collection:<folder>`, titled by the folder name, the folder its primary role) containing those movies. A folder that stops being one is deleted when nothing is left in it. `prepare()` lists the folders around each video (`os.scandir`, cached per batch) to tell which.
   - A video already linked to a movie updates it in place (a rename or move follows the movie). Fields: Movie `year`, `folder`; Actor (`Name`) `born`, `country`. Actors and the cast come from .nfo files (#258) and by hand (#260).
   - **Pictures** (#124): in a movie's folder, its **poster** is the best of `poster`, `…-poster`, `folder`, `cover`, `movie`, `default`, or a picture named like the movie; its other pictures, and those in a `screenshots`, `screens`, `extrafanart`, `stills`, or `backdrops` subfolder, are **screenshots** (role `screenshot`, many). Beside loose videos, `Heat (1995)-poster.jpg` (else `Heat (1995).jpg`) is that movie's poster and `-fanart`, `-landscape`, `-thumb`, `-banner`, `-background`, `-backdrop` pictures its screenshots; a picture named after no video there is linked to nothing. A collection's folder picture (`poster`, `folder`, `cover`…) is its **poster** (a role beyond the sketch above, so it isn't left unlinked). An actor's photo is Kodi's `.actors/First_Last.jpg` in a movie's folder: it fills the `photo` role of the actor of that name, made if new (the photo may be read before the .nfo naming them, and a theme can't look a file up by path). A picture is matched to its movie by the movie's key, else by the same name in the same folder, else it makes the movie (its video may come later in the scan). Which picture is the poster is decided when a picture is read: adding a better-named one later replaces the poster, and the old one becomes linked to nothing until it is read again.
   - **Genres as file keywords** (theme version 3, #295): the .nfo's `<genre>` elements are reported with `ctx.keywords` (§7 *File keywords*); the Genre field is unchanged.
   - **.nfo files** (#258): `movie.nfo` in a movie's folder, or an .nfo named like one of a movie's videos, is linked in its `nfo` role ("Details file") and read in `prepare()` with the standard library's `xml.etree` (at most 1 MB; text after `</movie>`, such as Kodi's scraper URL, is ignored). It gives `title`, `year` (else the year of `premiered`), `plot` (else `outline`), `genre` and `director` (several joined with commas, searched as text), `runtime` (minutes in the file, stored in seconds, shown as `2:28:00`), and `rating` (else the default one of `<ratings>`). These win over the file name: a video read again doesn't rename a movie whose .nfo names it; values the user edited still win over both. Its `<actor><name>`s, in `<order>`, are the **cast** (actors keyed by normalized name, so one actor's movies meet); its `<set>` (`<name>` or plain text) is a **collection** of that name (key `set:<name>`) holding the movie. Reading it again replaces the cast and set it gave: an actor it drops leaves the cast, and is deleted if then in no movie and without a photo; a set collection left empty is deleted. An .nfo named for no movie is left unlinked; one that can't be parsed is still linked, with a warning.
   - **Video details** (#259, theme version 2): `prepare()` reads each video with MediaInfo, one at a time (a lock, #292: MediaInfo's options are process-wide, and parsing on two of the scan's reading threads at once crashed the process on macOS): its `runtime` (seconds), `resolution` (`1920 × 800`), `quality` (`4K`, `1440p`, `1080p`, `720p`, or `SD`, by width or height, so a letterboxed 1920 × 800 film is 1080p; a choice filter, and a card line after the year), `video_codec` (choice), and `audio` (its tracks' languages, `English, French`). A movie with several versions shows its best one's (the most pixels, kept in a hidden `pixels` field) and the longest runtime; an .nfo's runtime wins over the videos'. A file MediaInfo can't make sense of gives nothing, and one it fails on is still a movie, with a warning. Keeps made with version 1 read every file again once after the upgrade.
   - **Cast by hand** (#260): a related section (Cast on a movie's page, Filmography on an actor's) is an embedded search (§12) with an **Add…** button, and **Remove from cast** on its items' menus (several at once, as one step). Add… opens a dialog (`ui/relate_dialog.py`) that searches the other side's items as you type (those already there are greyed out) and offers "New actor: <name>" for the text typed. Adding and removing are each one undo step (`core/relations.py`) and are recorded in `user_relation`, so reading the movie's .nfo again neither removes someone added by hand nor brings back someone removed. A new actor is an item the user made (no ingest key), so scans never delete it, even out of every cast.
   - **Views** (#125), all grids sorted by title: **Movies** (`inherit_tags`, so a tag on a collection counts for its movies: tag The Lord of the Rings "Fantasy" and Movies with Fantasy lists its films), **Actors**, and **Collections**. An actor's page shows their fields and **Filmography** (the cast relationship from their side, as a list or a grid of posters, with Add… and Remove, #260); a movie's **Cast** is a list or grid of actors' photos; a collection's page lists its movies by year, then title (`contents_sort`). Movie cards show the year and quality.
   - **Pages and thumbnails:** a movie's page shows its fields, its videos, its cast (links to the actors), a gallery of its screenshots, and its .nfo, with the poster as its header picture. A movie's thumbnail is its poster, else its first screenshot, else the video icon; a collection's its poster, else one of its first five movies'; an actor's their photo.
5. **books** — Universe ⊃ Series ⊃ Book, Comic; Collection ⊃ Book, Comic; Author ↔ Book, Comic (M20, #293; designed in review; built in #296–#299). Fiction and nonfiction alike: novels, nonfiction, comics, stories, and documents.
   - **Types:** **Book** (EPUB, PDF, Markdown, DOCX, ODT, Pages, `.doc`, and link files) and **Comic** (CBZ, CBR, CB7), separate types like assets2d's, so views and fields can differ (a comic has an issue number and a story arc). **Author** (with `sort_name`, "Pratchett, Terry"). **Series**: works in reading order, by `series_index` (a float: 1, 2, 2.5). **Universe**: series and standalone works sharing a world (Discworld, Cosmere, Marvel). **Collection**: an omnibus or anthology holding works.
   - **Credits:** relationships from a work to its people, as cast is in the movies theme, with hand edits that stick (#260). A relationship joins two types, so each work type has its own pair (#296): `writers` and `artists` for books, `comic_writers` and `comic_artists` for comics. A work's page shows **Written by** and **Art by** (pencils, inks, colors, covers); an author's page has tabs **Books**, **Comics**, **Illustrated**, and **Comic art** (empty ones included, since a page's sections are declared per type). The work's `authors` (books) or `writers` and `artists` (comics) fields hold the names as the files give them, for cards, sorting, and filters.
   - **A work and its files:** a work is keyed by its normalized title and first writer (a comic by series, volume, and number; a work with no writer by title within its folder), so the same novel as an EPUB and a PDF, bought from two sites, is one work whose files are its versions (role `file`, many), as songs and movies have versions. **Files named alike in one folder** (`devops.epub`, `devops.pdf`; the name compared without case, book and comic formats but not link files) are one work whatever their details say, a download's formats of one book (#369): `prepare` lists the same-named files beside each file on disk, and `ingest` joins the work one of them already has (`ctx.resource_at`, `ctx.entities_of`) before keying by title and writer. Only a comic joins a comic and a book a book, and only a work that still has that file (a work merged away in Dedupe is still reported for its old files, so the file goes on to a sibling still linked to the work that was kept; #373). Author lists are split into people (`A, B, and C`: an EPUB creator often names everyone), and a publisher's placeholder (`AUTHOR NAMES HERE`, `Unknown`) is no author. A file already linked to a work updates it in place. **While a work has one file**, what the file says replaces what it said before: its title, fields, credits, series, universe, and collections (a series, universe, collection, or author left with nothing is deleted). **With several files**, each only adds (credits, collections, sources) and fills in what's missing, and the first file's title stays, so two stores' slightly different metadata don't take turns.
   - **Sources:** where a file was bought or downloaded. The theme option `source_level` names the folder level that is the site (0, the default: none; `1` for `Humble Bundle/…`), else front matter's `source`, the site of ComicInfo's `Web` (its host name), or EPUB's publisher. A work's `sources` field lists its files' sources ("Humble Bundle, Kobo"). Showing each file's own source beside it on the page needs per-link values the theme API doesn't have yet; for now the files section shows their paths, which name the source folder.
   - **Different names for one writer:** one author per spelling, as the files give them; **merging** them (§13) keeps the merged names pointing at the kept author, so later files under either spelling land there. Pen names stay separate authors, related by hand.
   - **Reading files** in `prepare()`, by format (the order they are built in). Each reader is a **public helper in `tagalot.themes.api`** (decided in review: `read_epub`, `read_mobi`, `read_comic_info`, `read_pdf_info`, `read_front_matter`, `read_office_info`, `read_link_file`), not private to this theme, so the research theme (M21) and third-party themes read the same formats the same way. They only read, return plain values (dicts of what they found, with `None` for what they didn't), guard native libraries that aren't thread-safe with locks (§6: `prepare` runs on several threads), and are documented in THEMES.md as part of the API's contract:
     - **EPUB** (#296, built: `read_epub`, `epub_cover`): the OPF package (`zipfile` and `xml.etree`): `dc:title`, `dc:creator` (with its role, from `opf:role` or an EPUB 3 `refines` meta: `aut` writer, `ill` and `art` artist, `edt`, `trl`; no role counts as a writer), `calibre:series` and `series_index` or EPUB 3 `belongs-to-collection` (type `series` is the series; other types, such as `set`, are collections), `dc:subject` (keywords), `dc:publisher`, `dc:language`, `dc:date`, `dc:identifier` (ISBN), `dc:description` (HTML removed), `dc:source`; the cover from the manifest's `cover-image` (or `meta name="cover"`). Package documents over 2 MB aren't read.
     - **Kindle and Mobipocket** (#370, built: `read_mobi`, `mobi_cover`, `themes/mobi.py`; `.mobi`, `.azw`, `.azw3`, API version 7): a Palm database (`BOOKMOBI`), read with `struct`, record by record (a book on a share isn't read whole for its details). Record 0's EXTH block gives the details: author (100, one record per author, each as written, so through `split_people`), publisher (101), description (103, HTML removed), ISBN (104), subjects (105, keywords), date (106, the year), ASIN (113), updated title (503, else the MOBI header's full title, else the database name with `_` as spaces), language (524); the cover is the record EXTH 201 (else 202, the thumbnail) names past the first image record, else the first image, checked to be a picture. DRM encrypts only the text records, so a protected book's details and cover read as any other's; `encrypted` says so. Its text (for search inside documents) is its text records, each without its trailing entries (the MOBI header's extra-data flags), unpacked (PalmDOC; HUFF/CDIC, #375; or none), split at `<mbp:pagebreak/>` into chapters, markup removed; protected books raise `ValueError`, listed as **Text not read**. **HUFF/CDIC** (Amazon's tools: kindlegen, Kindle Previewer, KDP) is a Huffman code over a dictionary of phrases: the MOBI header names the HUFF record and how many records follow it (record 0 at 0x70 and 0x74); the HUFF record has a 256-entry table by a code's first byte (its length, whether that's final, the highest code of that length) and each length's lowest and highest codes; the CDIC records hold the phrases, each literal or itself compressed (decoded on first use; a phrase that leads back to itself is refused). Longer codes are numerically lower; a phrase's index is its length's highest code minus the code. Not `.kfx` (a different, locked-down container) nor `.prc` (as often a Palm program). Our own reader, standard library only: the Python ones (KindleUnpack, `mobi`, calibre) are GPL.
     - **Comic archives** (#296, built: `read_comic_info`): `ComicInfo.xml` anywhere in the archive (`Series`, `Number`, `Volume`, `Title`, `Writer`, `Penciller`, `Inker`, `Colorist`, `CoverArtist`, `Publisher`, `Imprint`, `Genre` and `Tags` as keywords, `Web`, `Year`, `StoryArc`, `SeriesGroup` as the universe), read with the thumbnails' archive reader (§10 *Archives*: the format by content, the same size budgets, RAR needing its tool); the cover is the first page, drawn as any archive's. A comic without a `Title` is called "Series #Number".
     - **PDF** (#297, built: `read_pdf_info`, `pdf_cover`): the document info (`Title`, `Author` split into people on `;`, `&`, and `and` (commas only when each part is a full name, so "Pratchett, Terry" stays one), `Subject` as the description, `Keywords` split on commas and semicolons, the year of `CreationDate`) and the page count; the first page rendered as the cover, by extension as EPUBs are (§10). A damaged or password-locked PDF is a work named from its file name, and reported.
     - **Markdown** (#297, built: `read_front_matter`; `.md` and `.markdown`): front matter, YAML between `---` lines or TOML between `+++` lines, keys matched ignoring case: `title` (else the first `# heading`), `author`/`authors`, `series`, `series_index` (or `number`, `series_number`), `universe`, `tags`/`keywords` (a list, or text split on commas, else spaces; a leading `#` dropped, `Genre/Fantasy` kept as a path), `source`, `url`/`link`, `date` or `year`, `publisher`, `language`, `description`/`summary`, and `cover`; every key also comes back as written (`fields`), for themes' own keys. Only the first 1 MB is read. **Covers** (decided in review): `cover` is a picture path relative to the file (or to the root with a leading `/`; Obsidian's `[[cover.jpg]]` works too). The books theme scans pictures (`.jpg`, `.jpeg`, `.png`, `.webp`, `.gif`) so it can link the named one in the work's `cover` role (`ctx.resource_at`), and remembers the name in a hidden `cover` field, so a picture scanned later is linked then. Pictures no book names show in Triage's Unlinked files.
     - **DOCX and ODT** (#298, built: `read_office_info`, `office_cover`): `docProps/core.xml` / `meta.xml` (title, creator (ODT's initial creator, since its creator is whoever saved it last), keywords, subject, description, created, language) and their embedded thumbnails (`docProps/thumbnail.*`, `Thumbnails/thumbnail.png`). **Pages** (#298): a Pages file saved as one file (a zip) gives its preview picture (`preview.jpg`, `QuickLook/Thumbnail.jpg`); Apple's own format holds the rest, so the title is the file name. A Pages *package* (a folder) isn't read. Legacy **`.doc`**: the file name only.
     - **Link files** (#298, built: `read_link_file`), for works that live on the web (a serial on Royal Road or AO3): Windows `.url` (an INI file's `URL=`), macOS `.webloc` (a property list's `URL`), and Linux `.desktop` links (`Type=Link`, `URL=`). The address becomes the work's `link`; the title comes from the file name (Tagalot never visits the page, §14 *Metadata fetchers*). Opening one opens the address in the browser, as the operating system does for the file. A `.desktop` file that isn't `Type=Link` (an application's launcher) isn't a book; its `Name=` titles a link's work.
     - Without metadata, the file name: `Author - Title (Year)`, `Series 03 - Title`, comics as `Series #012 (2020)` or `Series v2 012` (the number without its leading zeros). A file that can't be read at all is still a work, named from its file name, and reported.
   - **Links:** a work's `link` field (`display="url"`, §9 *Fields*) holds its web address, from a link file, front matter's `url`, ComicInfo's `Web`, or EPUB's `dc:source` (only `http(s)` addresses). Clicking it on the work's page opens the page in the browser (#298).
   - **Online details** (built in #342, §9 *Online details*; API version 5): a book with an ISBN (10 or 13 digits: an EPUB's `dc:identifier`, or one the user typed in) is looked up in Open Library (`openlibrary.org/isbn/{isbn}.json`, its edition). It fills in only fields that are empty: year (from `publish_date`), publisher (the first), language (MARC codes such as `eng` as the two-letter codes EPUBs use), and description (text, or `{"value": …}`). Title, authors, series, and identifiers never come from it, so a lookup can't change which work a file joins; what a file says always wins (reading a file again replaces a looked-up value, and the lookup after that scan fills it again only if the file says nothing). Comics have no ISBN and aren't looked up. The demo's EPUBs carry real ISBNs (and Equal Rites one Open Library doesn't know).
   - **Keywords** from files (subjects, tags, genres) are reported with `ctx.keywords` and become tags only through **file keywords** (§7): defined tags they match, never new ones.
   - **Views:** **Books** (by author, series, and number) and **Comics** (by series, volume, and number), grids with `inherit_tags`, so a tag on a series or universe counts for its works; **Authors** (by `sort_name`, "Pratchett, Terry", made from the name and editable), **Series** (sorted by title, opening to its works in reading order: `series_index`, a comic's number as a number), **Universes**, and **Collections**. A work's page shows its fields, its files, its credits, and its keywords (§7); its breadcrumbs show its series. Thumbnails: a work its cover (an EPUB's named cover, else its best image; a comic's first page); a series, universe, or collection one of its first five works'. Near-duplicates: works with the same first writer, or the same title (one of a book's files may name no writer, or name them differently), whose titles are at least 85% alike (`difflib`), unless both have different numbers in a series, or both name writers and share none.
   - **Write-back** (#299): **Write to file…** on Markdown books in a writable folder (§4 *Writing back to files*) writes their tags and edited fields into the front matter: title, number in series (under `series_index`, or the file's `number` or `series_number`), year, publisher, language (or `lang`), ISBN, description (or `summary`), and link (`url`, or `link`). Author, series, and universe come from the files and credits, and aren't edited by hand.

6. **research** — Venue ⊃ Paper; Project ⊃ Paper; Author ↔ Paper, in order (M21, #306; designed in review; built in #317–#322 and #329: Project is made by hand, `made_by_hand`). Papers, preprints, theses, chapters, and reports, sharing the books theme's readers (§9 books).
   - **Types:** **Paper** (`kind`: article, preprint, thesis, chapter, report, book; `year`, `venue`, `volume`, `issue`, `pages`, `doi`, `arxiv`, `pmid`, `citekey`, a searchable `abstract`, `url` (`display="url"`), the author list as written for cards, and the user's `read_status` (Unread, Reading, Read) and `rating`, editable); **Author** (with `sort_name`); **Venue** (a journal or conference: its papers); **Project** (a reading list, made by hand, holding papers). Roles: `paper` (the PDF; many, the versions), `supplement`, `data`, `code`, and `notes` (literature notes).
   - **Authors in order** (decided in review): first and last author matter, so the theme API gains **ordered relationships** (API version 4, additive): `related(name, A, B, ordered=True)` gives the link table a `position`; `ctx.relate(name, a, b, position=n)` sets it, `ctx.related` returns the other side in position order, and a related section lists it in order. Adding by hand (#260) appends at the end, and Move up / Move down reorder by hand, kept through scans (built in #317, §9 *Containment and relationships*). Other relationships are unchanged.
   - **A paper and its files:** papers are keyed by identifier: DOI (lowercase, without `https://doi.org/`), else arXiv ID (without its version: `2101.01234v2` is `2101.01234`), else PubMed ID, else normalized title and first author's surname, else title within the folder. Before making a paper, the theme looks for one with any identifier the file gives (`ctx.find`), so a preprint and its published version are one paper with two versions once any source names both IDs, and duplicate downloads collapse. Two papers found to be one later are merged by hand; Dedupe lists papers sharing a DOI or arXiv ID, and same-first-author papers with similar titles, as near-duplicates.
   - **Reading a PDF** (#318): its document info (`read_pdf_info`), and identifiers found in its **first page's text**: API helpers `pdf_text(path, pages=1)` (PDFium's text, under the `PDFIUM` lock, at most 20,000 characters; a scanned PDF without a text layer has none) and `find_identifiers(text)` (the first DOI, lowercase, trailing punctuation dropped; arXiv ID, new and old style, without its version, also from an arXiv DOI `10.48550/arXiv.…` or a bare `2101.01234v2` file name; PubMed ID). PDF metadata alone is often empty or wrong: a title of "Microsoft Word - draft3.docx", "Untitled", or a file name is ignored, and so is an author that looks like a login (`jsmith`). The file name is the fallback: Zotero's `Author et al. - 2020 - Title.pdf` and `Author et al. (2020) Title.pdf` (title, year, and authors' surnames), or an arXiv download `2101.01234v2.pdf` (the ID; its year from the ID). The year comes from the file name, else the arXiv ID; a PDF's creation date isn't used (it is often the download's). `kind` is preprint while only an arXiv ID is known, article once there is a DOI. PDF keywords are file keywords (§7), a phrase such as "Language models" staying one keyword.
   - **Which source names a paper** (#318, generalized in #320): every file describing a paper is a **source**, and what each says is kept in the paper's hidden `origins` field (JSON: resource id → field → [rank, value]). Each detail (title, authors, year, kind, venue, volume, issue, pages, DOI, arXiv ID, PubMed ID, citation key, abstract, link) is the best-ranked source's that gives one: a sidecar bibliography (40), a library export (30), a PDF's document info and first-page identifiers (20), a named file (Zotero's pattern, 10), a bare file name (0); a literature note (#321) will rank above them, and the user's edits beat all (provenance). A source read again replaces only its own entry; sources no longer linked to the paper are dropped. `kind` comes from a bibliography, else from the identifiers (preprint, article).
   - **Bibliography files** (decided in review; built in #319, `themes/bibliography.py`): a new API helper `read_bibliography(path)` reads **BibTeX/BibLaTeX** (`.bib`: Tagalot's own reader for the common subset: entries, braced and quoted values, `@string` macros and `#`, LaTeX accents and braces turned into text, `and`-separated names, `Last, First` and `First Last`), **RIS** (`.ris`), and **CSL-JSON** (`.json` that parses as CSL items; other JSON is ignored) into plain entries: type, citekey, title, authors in order, year, venue, volume, issue, pages, DOI, arXiv ID, PubMed ID, URL, abstract, keywords, and the file paths it names. It is written so that **bibtexparser** can replace the BibTeX part later if people need more of BibTeX, without changing what it returns (themes see only the helper). As built: every entry has the same keys whatever the format (`type`, `kind`, `citekey`, `title`, `authors` and `editors` as `First Last` in order, `year`, `venue`, `volume`, `issue`, `pages`, `publisher`, `doi`, `arxiv`, `pmid`, `url`, `abstract`, `keywords`, `files`); `kind` is article, preprint, conference paper, chapter, book, thesis, report, web page, or other ("conference paper" and "web page" join the design's list, since exports distinguish them). An entry known only on arXiv (no DOI) is a preprint, whatever type Zotero (`@article` with journal "arXiv preprint …") or Better BibTeX (`@online`) gave it, and "arXiv …" isn't kept as its venue. DOIs are normalized as `find_identifiers` does (an arXiv DOI gives the arXiv ID); BibLaTeX's `eprinttype` gives arXiv and PubMed IDs. File fields are read in Zotero's (`desc:C\:\\…:type`), JabRef's (`:path:PDF`), Mendeley's (`$\backslash$`), and Better BibTeX's (plain paths) forms; RIS file links (`L1`–`L4`, `file:///…`) become paths. A broken BibTeX entry is skipped and reading goes on at the next `@`; a `.json` file that isn't CSL-JSON gives no entries. Files over 64 MB aren't read.
   - **Which bibliography files describe papers** (decided in review: Zotero and other managers' exports are supported):
     - A **sidecar**, named like the paper's file in the same folder (`smith2020.pdf` and `smith2020.bib`, `.ris`, or `.json`), describes that paper.
     - Any other bibliography file is a **library export** (Zotero, including Better BibTeX's auto-export, Mendeley, JabRef). Each entry is matched to a paper by its file field (the end of the exporting computer's path matching a paper file's path in the root: Zotero's `storage/K7X2ABCD/Smith 2020.pdf` matches `K7X2ABCD/Smith 2020.pdf` in a root watching Zotero's storage folder), else by DOI, arXiv ID, or PubMed ID. Entries matching no paper are ignored: papers without files stay future work (§14). Tagalot reads exports, not Zotero's own database.
     - Matching works whichever is read first (built in #320; chosen in review over keeping entries as hidden items): the theme lists bibliography extensions in **`Theme.read_last`** (API version 4), so a scan reads them after its other files, and reads every one of them again in a scan that read other files of their root (§6), so an export meets PDFs added since. A scan that finds nothing new doesn't re-read them. A matched paper links the bibliography file in its `bibliography` role ("Bibliography files" on its page, which is where its details came from); on the next reading, a paper whose entry is gone is unlinked and its details from that file dropped. An export's entries are matched by the file paths they name (the longest ending of the path, up to six parts, that is a file of the root: `ctx.resource_at`), else by DOI, arXiv ID, or PubMed ID (one look-up table per export). A sidecar is a bibliography named like a `.pdf` beside it; its entry is the one naming that PDF, else its first.
     - **Which source wins** for a field: the user's edits, then a literature note, then a sidecar, then a library export, then online details (#341), then the PDF itself, then the file name (see *Which source names a paper* above). Keywords from a bibliography entry are that file's keywords for the paper (§7).
     - **Venues** (#320): a paper is in the Venue its best source names (a journal, proceedings, or book series), and a venue left empty goes. **Venues** view, sorted by title; a venue's page lists its papers newest first.
   - **Literature notes** (built in #321): a Markdown file (`.md`, `.markdown`) whose front matter names a `citekey` (also `citationkey`, `citation-key`; Obsidian's leading `@` dropped), `doi`, `arxiv`, or `pmid` is linked to that paper in its `notes` role, matched by DOI, arXiv ID, PubMed ID, or citation key (the key a bibliography gave the paper). What it says is the paper's best-ranked source (50, above a sidecar): `title` only from front matter (a heading titles the note, not the paper), `authors`, `year`, the venue (`journal`, `venue`, `booktitle`), the link, and its identifiers. Its `tags` are the paper's file keywords (§7). Notes are read last, after bibliographies: `read_last` may be a tuple, read in its order (§9 *Theme*), so a note meets the citation keys an export gives in the same scan. A note naming no known paper stays unlinked (Triage's Unlinked files lists it); a Markdown file whose front matter names no paper isn't a note; a note that stops naming its paper lets go of it.
   - **Actions** (built in #322): **Copy citation** (one plain style: `Vaswani, A., Shazeer, N., & Parmar, N. (2017). Title. Venue, volume(issue), pages. https://doi.org/…`, papers separated by a blank line; more styles later), **Export BibTeX…** for the selection (a file the user saves, `papers.bib` or the paper's citation key; a place inside a watched folder is allowed after a warning and then skipped, §4 *Saving an export*; entries round-trip through `read_bibliography`, with the paper's citation key, else one made of the first author's surname, the year, and the title's first word, made unique with a, b, …), **Open DOI page** (`https://doi.org/…`, else the arXiv page, else the paper's link; at most 10 at once; in the browser). Citations between papers by hand: `cites` (Cites / Cited by, with a direction) and `related` (symmetric); a cited paper not in the keep can be added by name from Add… (an item the user made, without files). Extracting citations from PDFs is a separate project.
   - **Online details** (built in #341, §9 *Online details*): a paper with a DOI is looked up in Crossref (`api.crossref.org/works/{doi}`); one with only an arXiv ID in arXiv (`export.arxiv.org/api/query?id_list=…`, every 3 s as arXiv asks). A preprint that has a DOI is looked up only in Crossref: the published record is the better one, and it halves the requests. What a service says is one of the paper's sources, under `online:crossref` or `online:arxiv` in `origins` (kept through scans, unlike a file no longer linked), ranked 25: between a library export (30) and the PDF (20). It gives the descriptive details only (title, authors, year, kind, venue, volume, issue, pages, abstract; Crossref's JATS abstract as plain text), never identifiers, so a lookup never changes which paper a file joins. A service that doesn't know the paper (Crossref's 404, arXiv's empty feed) lets go of what it said before. API version 5.
   - **Views:** **Papers** (a list, newest first, built), **Authors** (by sort name, built), **Venues** (#320), and **Projects** (#329); a paper's page shows its fields, its versions and supplementary files, its authors in order, its notes, and its keywords. Reading lists by status are saved searches. Thumbnails: a paper its first page.
   - **Demo:** `make_demo_keep.py --research` (`just demo-research`, built with #318): small PDFs with a text layer holding DOIs and arXiv IDs, one paper downloaded twice, a preprint and its published version, a junk document title, and a PDF with no metadata; a sidecar `.bib`, a Zotero-style export, and a literature note come with #320 and #321.

## 10. Thumbnails

### Resolution

Each entity type has an ordered **provider chain** from the theme. Providers return an image source or "no result". Typical chains:

- **Song:** embedded art (ID3 APIC, FLAC picture, MP4 `covr`) → parent Album's thumbnail → generic audio icon.
- **Album:** folder image by convention → embedded art of first track → icon.
- **Actor:** `photo` role → icon.
- **Movie:** `poster` role → first `screenshot` → icon.
- **Collection** (movies): `poster` role → one of its first movies' thumbnails → icon.
- **Archive asset:** first suitable image inside the archive → icon.

Renderers by kind: image, audio (embedded art), archive (best image inside), font (a sample: "Aa" and "Quick fox" on a light square). Formats that are no kind of their own have renderers by extension, tried first (`EXTENSION_RENDERERS`, #296): an EPUB shows the cover its package names, else its best image as an archive would; a PDF its first page (#297); a Word, OpenDocument, or Pages file the preview it keeps (#298). EPUB isn't added to the archive kind, since themes that accept archives (assets2d) would then take in books. Built-in providers: `RoleImage(role)`, `FolderImage(names)`, `EmbeddedAudioArt()`, `ArchiveFirstImage()`, `ParentThumbnail()`, `ImageFile()`, `Icon(name)`.

**Providers choose; renderers draw.** A provider is a `ThumbnailProvider` subclass (in `themes/api.py`; themes may write their own) whose `candidates(entity, ctx)` yields resources to try, best first. It only chooses: the core turns a resource into a picture with the **renderer for its kind** (`core/thumbnails/render.py`: an image is decoded, an archive shows its first image, an audio file its embedded art; kinds without a renderer never give a picture). The runner (`core/thumbnails/resolve.py`) tries each candidate in turn, skipping ones already tried, then the next provider; the first picture wins. `Icon(name)` ends the chain (`name` is a kind value, `"file"`, or `"entity"`; a chain without one ends in `"entity"`). A provider that raises is logged, reported, and skipped.

- **Context** (`ThumbnailContext`, read-only): `resources(entity, role=None)` (linked resources in sort order, leaving out missing files), `primary_role(entity)`, `parents(entity)`, `children(entity)` (by title), `folder_files(entity, extensions=None)` (files directly inside the entity's folder, by name: the folder of its primary resource, or that resource when it is a folder), and `thumbnail_of(entity)` (another entity's resolved source; containment cycles give `None`).
- **Default chain** (`default_thumbnail_chain`): `RoleImage` for each role marked `thumbnail=True`, then `ImageFile()` (the primary role's resources) unless the primary role was already listed, then `Icon` of the primary role's single kind (`"file"` for several or `any`, `"entity"` with no primary role).
- **The built-ins:** `RoleImage(role)` offers the role's resources; `ImageFile()` the primary role's (drawn by kind, so it also covers audio art and archives); `FolderImage(names=FOLDER_IMAGE_NAMES)` pictures in the entity's folder named by convention (below); `EmbeddedAudioArt()` the entity's own audio files, or, when it has none (an album), the audio of its first three contained items that have any; `ArchiveFirstImage()` the entity's archive files; `ParentThumbnail()` the resource each parent's thumbnail comes from.
- **Renderers:** `image` decodes with Pillow (JPEGs at a reduced scale via `draft`); `audio_art` reads embedded pictures with mutagen: ID3 `APIC`, FLAC pictures, MP4 `covr`, and Ogg/Opus `metadata_block_picture`, preferring the one marked front cover (type 3), else the first. The archive renderer is `ArchiveReader` (below).
- **Validation:** the loader checks each entity type's chain holds only providers and that `RoleImage` roles exist.
- **Failures:** a file that can't be read is reported (path and error, for the activity panel) and not retried in that session until it changes.

### Folder conventions

Case-insensitive, any of `.jpg .jpeg .png .webp` (`FOLDER_IMAGE_EXTENSIONS`): `folder`, `cover`, `front`, `albumart`, `AlbumArt_*_Large`, `AlbumArtSmall` (`FOLDER_IMAGE_NAMES`, in order of preference; `*` is a wildcard). Themes can extend the list: `FolderImage([*FOLDER_IMAGE_NAMES, "poster"])`. Only scanned files are known (no directory listing at thumbnail time, so network shares aren't walked again and the chosen file can be memoized), so a theme using `FolderImage` must include these extensions. Subfolders (`scans/folder.jpg`) don't count.

### Archives

- List members; skip directories, `__MACOSX/`, dotfiles, and non-images.
- Prefer names containing `cover`, `preview`, `thumb`; otherwise the first image in natural sort order.
- Read only the chosen member. Zip supports random access; solid 7z/RAR may need to decompress preceding data, so archive thumbnails always run in workers with a size/time budget and give up gracefully.
- **Implementation** (`core/thumbnails/archive.py`): `ArchiveReader` has zip (`zipfile`), 7z (`py7zr`, extracting one member into memory), and rar (`rarfile`) implementations, chosen by the file's first bytes rather than its extension (many `.cbr` files are zips). Preferred names are ranked `cover`, then `preview`, then `thumb`; ties and the rest go in natural order (`page2` before `page10`), case-insensitively.
- **Budgets:** images over 64 MB uncompressed are skipped (the next candidate is tried); in a solid archive, if more than 256 MB comes before the chosen image, the archive shows no picture. Encrypted members are skipped.
- **Rar:** listing needs no tool, but reading a compressed member needs `unrar`, 7-Zip, or `bsdtar` on the `PATH`. Without one, rar archives show their icon; this is logged once, not reported for every file.
- A file that isn't a readable archive, or a damaged member, is reported like any unreadable file.
- **Galleries** (planned, M28, §9 *Galleries*) list every picture in an archive, with the same budgets, and cache each one's thumbnail by the archive, the member's path, and the archive's size and time.

### Sizes

- **Maximum** (`Theme.thumbnail_max`, default 256; a keep can override it in `keep.toml`, §4): the resolution thumbnails are made and cached at. It is part of the cache key, so changing it regenerates thumbnails as they are shown. Themes with detailed pictures (2D assets) set it higher, up to 2048.
- **Display size** (`Theme.thumbnail_default`, default 128): how big grid cards start. The user picks **View → Thumbnail size**: Small (64), Medium (128), Large (256) (presets below the maximum), and Largest (the maximum); or zooms with Ctrl+wheel over the grid, Ctrl+= / Ctrl++ and Ctrl+-, stepping through 48, 64, 80, 96, 128, 160, 192, 256, 320, 384, 512… up to the maximum. The choice is remembered per keep in `ui_state.json` (`thumbnail_size`). Cards draw the cached image scaled down (never up), so zooming reads nothing.
- The loader checks `16 ≤ thumbnail_default ≤ thumbnail_max ≤ 2048`.

### Cache

- `thumbs.db` table `thumb(key text pk, size int, format text, width int, height int, data blob, created_at)`. `size` is the thumbnail size asked for; `width`/`height` are the stored image's, so views can lay out a cell before decoding it.
- `key = sha256(resource_id, size, mtime_ns, renderer_id, renderer_version, thumb_size)`, so changed files and renderer upgrades invalidate automatically. The size and time are the ones the last scan recorded, so no file is read to check them: a file edited since then keeps its old thumbnail until a scan notices the change. The time alone is enough (an edit that keeps the size still gets a new key). (The renderer, not the provider, decides the pixels, so it is the renderer's version that counts.) Stale entries are never read, only removed by clearing the cache.
- Thumbnails are fitted inside a `thumb_size` square (never enlarged, at least 1 px per side), turned upright by EXIF orientation, converted to RGB or RGBA (transparency kept), and stored as WebP quality 80 (PNG when Pillow lacks WebP). The entire file can be deleted at any time.
- `thumbs.db` is separate from `keep.db` and is written directly by the thumbnail workers (one short transaction per thumbnail, serialized by a lock), not through the DB writer: it shares nothing with the keep's data, and losing it costs only regeneration. It uses `PRAGMA synchronous = OFF` and records its format in `PRAGMA user_version`; a damaged file or another format version is deleted and started afresh.
- The resolved source resource is memoized in `entity.thumb_resource_id` to avoid re-running the chain. The runner tries the memo first; if it no longer gives a picture, the chain runs again and a different result is written through the DB writer (queued, not awaited). An offline memo without a cached picture keeps the memo and shows the chain's icon (offline isn't gone). Ingest clears an entity's memo whenever it links or unlinks a resource, so a new cover is chosen afresh. Entities that end in an icon have no memo and re-run their chain (database lookups only; unreadable files aren't retried).
- Cached pictures are used whatever the resource's status; files are only read when the resource is online (`ok`).
- **Clearing** (#78): **Keep → Clear thumbnail cache…** counts the stored thumbnails in a worker, asks ("Delete 1,234 stored thumbnails (45.6 MB)?"; nothing to ask when the cache is empty), then deletes them and shrinks the file (`VACUUM`) in a worker. It also forgets which files failed this session, so they are tried again, and the window's loaded thumbnails, so the grid refills as it is shown. Memoized sources (`thumb_resource_id`) are kept: the choice of file is still right, only the pictures are remade. It is the **Clear…** button on the Keep configuration window's Thumbnails tab (§12), which also shows how many are stored.

## 11. Opening files

- **Default:** hand the file to the OS via `QDesktopServices.openUrl(QUrl.fromLocalFile(...))`. This supports UNC and mapped paths.
- **Always available:** "Reveal in file manager" and "Open with…" (one-time choice).
- **Which file** (#104, `core/handlers.py`): an item opens its type's primary role's files (else any it links), the first that was there at the last scan and has a path on this computer, in the role's sort order (a song's first version). Otherwise the status bar says why: no files, the root was offline, the file was missing, or the root has no path here. The lookup runs in a worker; the launch happens on the GUI thread without waiting for the program (`QDesktopServices` for the default, detached processes otherwise).
- **Where** (`ui/file_actions.py`): a result's right-click menu and the detail page's More menu have **Open file**, **Show in file manager**, and an **Open with** submenu (an item whose primary role holds folders, an album, has **Open folder** and **Show in file manager**; a type without roles has none). Each file row on a detail page has the same menu for that file (a particular version). The window's `FileOpener` is handed to its pages (`page.file_opener`).
- **Open with** is filled when first shown, once a worker has found the file: **Choose a program…** (this once, below), **Always open .ext files with…** (pick a program; it becomes a per-user override for that extension), and, when an override applies to the file, **Stop using <program> for .ext files**.
- **Show in file manager:** Windows `explorer.exe /select, <path>`, macOS `open -R <path>`; Linux has no common way to select a file, so its folder is opened.
- **Choose a program…:** Windows shows its own "Open with" dialog for the file (`SHOpenWithDialog`, the choice not remembered); macOS asks for an application in `/Applications` (`open -a`); Linux asks for a program and runs it with the path. Nothing is remembered: lasting choices are overrides (below).
- **Overrides:** optional per-user rules keyed by extension (and optionally role) with a command template, for example `"C:\Tools\viewer.exe" "{path}"`. Placeholders: `{path}`, `{dir}`, `{name}`. Stored in per-user settings, not the keep.
  - **Applied** by Open file (#105): a rule for the file's extension and the role the item links it in wins over one for the extension alone (§4); folders never use one. Show in file manager and Open with ignore them.
  - **Templates** (`core/handlers.py`): split into words at spaces, with double quotes grouping (and removed) and backslashes ordinary, so Windows paths need no escaping; placeholders are filled in each word, so a path with spaces stays one argument; a template without placeholders gets the path as its last argument. The command starts detached; an empty or broken template is reported in the status bar.
  - **Made from the menu:** Always open … with… writes `"<program>" "{path}"` (`open -a "<app>" "{path}"` for a macOS application) for the extension alone, replacing any rule for the same extension and role, and saves `settings.toml` in a worker. Per-role rules and other templates are written by hand; **Stop using** removes whichever rule applied.
- **Archive members** (when supported): extract the single member to a temp directory, then open it.
- **Gestures** (#107): single click selects; double-click (or Enter) opens the entity page, or its file (as Open file does, §11) if the type's `double_click="open_file"` and it can link files; Ctrl+Enter does the other. That holds in lists, grids, trees, Search all's sections, and contents searches. Enter and Ctrl+Enter are shortcuts on each view (keypad Enter too; Ctrl is Cmd on macOS), so Enter opens on macOS as well, where item views otherwise don't treat Return as opening. An item with no files opens its page either way. The right-click menu's bold default (`Open page` or `Open file`) is what double-click does. Inside a detail page's role sections, double-clicking a file opens that file. The preview strip's double-click always opens the page.
- Tagalot never writes, moves, renames, or deletes files under a root.

- **The theme's cards** follow the built-in ones, three to a row (§9 "Dashboard cards").
- **Reading:** one read in a worker; again when the page is shown again, on Refresh, and after tagging, undo, a scan, or a configuration change.

**Search view.** Filter bar with include chips, exclude chips ("but not"), field filters (only valid ones for the scope), `Within` chip, text box, toggles for "Show contained items", "Inherit tags", and "By contents" (`aggregate_up`). Results as grid (thumbnails), list (columns), or tree/grouped. Multi-select supported.

- **Results model** (`ui/models/results.py`): setting a search counts the matches and loads the first page (100 rows) in a worker, in one read transaction; the row count is then the full total, so the scroll bar is right at once. Other pages load in workers when the view first asks for one of their rows, which show `…` until then; the 50 most recently used pages stay in memory. Each search has a generation number and older results are dropped. After a scan, open search pages re-run their search, keeping their rows until the new ones arrive. A refresh that finds the same number of results (the usual case after tagging) updates the rows in place, so the selection and scroll position stay; when the count changes, the model resets and the page re-selects the items still listed (on loaded pages). Search all's sections re-select the same way when rebuilt.
- **List layout**: the title column, named by the type's `title_label` when the scope has one; a Type column when the scope has several types; then the `card=True` fields every scoped type has. Clicking the title or a field column sorts by it (the type column doesn't sort). The title column stretches to fill the width; the others start at fixed widths (narrower for numbers) and can be resized, never sized to contents, which would read every row. The generic theme shows Name, Extension, Folder (the parent folder within the root), Size (as a size: `display="bytes"`), and Modified.
- **Field filters** (#94, `ui/field_filters.py`): a **+ Field** button on the filter row lists the searchable fields every listed type has (`scope_fields` with a `search` kind; disabled, with a tooltip, when there are none, as in a Search all over types without shared fields). Picking one opens a small popup under it: a **choice** field lists its values among the current results with counts, most common first (`core.search.choice_counts`, in a worker; the field's own filter is left out of the counts, so other values stay offered; up to 500), each with a checkbox; a **range** field has From and To boxes (either may be empty, parsed like edited values); a **text** field has "contains" or "starts with" and a box. **Apply** (or Enter) adds a purple chip after the Within/Only chips and before the tag chips ("Extension: .png, .jpg", "Width: 500–1920", "Width ≥ 500", 'Folder contains "ice"'); clicking a chip reopens its popup, × or **Clear** in the popup removes it, and Clear all removes them all. A chip whose field the listed types no longer all have (after an Only chip, say) stays, dashed and grey with a tooltip, and isn't applied until the scope has the field again. Field filters are filters, not view settings: they aren't remembered.
- **Toggles** (#91, #133): **Contained** (show contained items, §8), **Inherit tags**, and **By contents** (a container matches when anything inside it does: albums with a song tagged *Live*; `aggregate_up`, §8) are checkboxes at the right of the filter row, with tooltips saying what each does. A page starts with its view's `show_contained` / `inherit_tags` / `aggregate_up` (off for Search all and a detail page's contents); what the user chooses is remembered per view in `ui_state.json` (`toggles`: `{"view:Images": {"show_contained": false, "inherit_tags": true, "aggregate_up": false}}`) and saved with saved searches. They are view settings, not filters, so Clear all leaves them. When contained items are listed, and the listed types can hold other types, the list gains a **Type** column (an artist's images and fonts are told apart).
- **Tree layout** (#91, `ui/result_tree.py`): the third layout button. The top level is the search's own results (the list's lazily paged model), leaving out those another result holds (`nest`, §8); a container's row expands to what it directly holds, loaded in a worker on first expansion (`core.search.child_hits`: every type, in the container's `contents_sort` order (by title unless the theme says otherwise, §9), not re-filtered by includes, text, or fields, but without excluded items, inherited when Inherit tags is on; up to 1,000). Children can expand in turn. When the page refreshes (after tagging, undo, or a scan), expanded containers' children are loaded again: the same items are updated in place (keeping what is expanded and selected), and items that came or went replace the rows. The tree lists contents as children, so **Contained is greyed out in the tree** (its tooltip says why) and the top level isn't flattened; it has a Type column when the listed types can hold others. Selection, the preview strip, tagging (the Tags panel, drops with the dashed outline), double-click, and the right-click menu work on any row; sorting by a column sorts the top level. Search all's sections stay lists (the tree button is disabled there), and a view can start as a tree (`SearchView(layout="tree")`); the choice is remembered like the others.
- **Grid layout** (#77): cards in wrapping rows of one uniform size, each a thumbnail (or its icon while there is no picture; a faint placeholder while loading) above the title and the **card lines**, elided to fit; the tooltip lists the title and every card line with its label. It shows the same model as the list and **shares its selection**, so switching keeps what is selected, and it accepts dropped tags like the list (dashed amber outline). It is a `QListView` in list mode with wrapping and uniform item sizes, not icon mode, which would store a position for every item.
- **Switching layouts:** two icon buttons at the right of the page header, next to the count. A view starts in its declared `layout` (`grid` or `list`); the user's choice is remembered per view in `ui_state.json` (`layouts`). Search all's sections stay lists (the buttons are disabled there); the choice applies once one type is shown.
- **Card lines:** by default each type shows its theme's `card_lines`. Right-clicking the grid offers **Card lines**, a checkbox for each field of the listed types, and "Use the theme's card lines"; the user's choice is a list of field names (each type shows those it has), remembered per view in `ui_state.json` (`card_lines`). The fields load with each page of rows even when no column shows them. Values show as in list cells until field display formats arrive (#184).
- **Thumbnail loading** (`ui/thumbnails.py`): one `ThumbnailLoader` per window resolves thumbnails on its own pool of 4 threads, so thumbnails never delay searches. Painting a card requests its entity; the **newest requests go first** (scrolled-past requests wait, and more than 400 waiting drops the oldest), and up to 600 decoded images are kept (LRU). Arrivals repaint the grid at most every 30 ms. After a scan the loaded thumbnails are forgotten (files may have changed); on closing, the window waits for running thumbnail jobs before the keep closes.
- **Tags column and hiding columns** (#197): every list (and each of Search all's sections) has a **Tags** column, right after the title (and Type), listing the tags applied directly to the item by name (the path when a name is ambiguous), with full paths in the tooltip; it isn't sortable. Tag names load with each page of rows, in the worker (`row_values`, `core.tags.entity_tags`), and refresh after tagging. Right-clicking a column header shows every column with a checkbox (the title can't be hidden). **Tags starts hidden**; what the user shows or hides is remembered per view in `ui_state.json` (`hidden_columns`: `{"search:": [...], "view:Files": [...]}`) and applies to the list and every section of that page. **Every field is a column** (#314; asked for in review): after the title, Type, Tags, and Keywords come the fields the scoped types share that their pages show (not `detail=False` ones), card fields first and shown, the rest **hidden until shown** from the header menu (`ResultColumn.hidden_by_default`), so Books' Link, Description, or ISBN, or Music's Bitrate, can be listed and sorted. Showing one is remembered per view as `shown_columns` (`{"view:Books": ["link"]}`), beside `hidden_columns`; a column the user hid stays hidden.
- The heading shows the view's name and "N items" (or "Nothing found", or the error for a search that can't run, such as one sorting by an unknown field).
- **Filter bar** (`ui/filter_bar.py`): a text box and a tag box on one row, with chips below that wrap onto more lines. Typing in the tag box lists matching tags (`TagTree.suggest`: name or alias contains the text, ranked whole name, start of name, start of a word, anywhere, then the same through an alias; each shown with its parent path). **Enter adds an include chip; Shift+Enter adds a "but not" chip**, the same keys the tagging panel uses to apply and remove tags; Up/Down move, Esc closes the list. Include chips are blue, exclude chips red with "not:"; a tag added to the other list moves there; × removes a chip; "Clear all" removes every chip and the text. The text box applies 300 ms after typing stops, or on Enter; Ctrl+F focuses it. Filters apply on top of the view's own spec, keeping its types, toggles, and current sort. The suggestion list is a child widget of the window rather than a popup window, so it never takes focus from the tag box. The tag tree is loaded in a worker and reloaded when the page refreshes. The `Within` chip is described under "Drilling down", the toggles under "Toggles".
- **Global search, grouped** ("Search all", `ui/grouped_results.py`): one collapsible section per type that has matches, in the theme's type order, headed `▾ Album (40)`. Each shows the type's first 8 matches with **that type's own list columns** (Albums show Year, Artists Country), and "Show all 40 →" when there are more. Show all narrows the page to that type with a removable **"Only: Album" chip** (first in the chip row; Clear all removes it too), showing the full lazily paged, sortable list. When only one type matches (always, for a one-type theme such as generic), its full list shows directly, without a chip. Counts and previews come from one worker job in one read transaction. Folded sections stay folded when the results change (for the session, not saved). Section headings and the Only chip use the type's plural name (`Entity.plural`, §9); the Type column uses its singular `label`. A sort chosen on one type's list (Year) is kept while the listed types have that field, and otherwise the page's default sort applies; theme views are never grouped.

**Detail page.** Theme-declared sections: fields (inline edit; user edits set provenance `user`), role slots (drop files to link), galleries, related entities, and for containers an embedded search of contents with its own filter bar. Header shows breadcrumbs and actions.

- **Rendering** (#86, `core/detail.py` + `ui/detail_view.py`): a header with the thumbnail (192 px box, from the window's thumbnail loader) beside the title and type and the item's note (#380, `ui/note_view.py`: its body as rendered Markdown under the title, capped at the room beside the picture with **Show more**/**Show less** to expand it in place; relative links and pictures resolve from the note's folder, read only; **Open note** under it and in **More ▾**), then the sections top to bottom, full width, in a scroll area; each section is a bold heading with a rule. `load_detail()` reads everything in one worker job. The type's `DetailView` gives the sections; without one, `default_detail_view()` shows its fields, its primary role, and (for a type that can contain others) its contents.
  - **Details** (`Section.fields()`): each field with `detail=True`, label and value; omitted for a type without fields.
- **Re-reading from files** (#96, `core/reextract.py`): **Re-read from file** (a result's right-click menu, for the selection when the item is in it, and a detail page's **More ▾** menu) marks the items' linked files pending and ingests them at once through the theme (`scanjob.ingest_pending`, with the root's theme options), without walking the root: useful after changing a file, or to refresh what a scan read. Fields the user edited keep their values. **Re-read from file, replacing my edits…** asks first ("Edit → Undo can put your edits back"), then clears the `user` provenance on those items so the files' values (title included) win. Either way it is **one undo step**: the step holds each item's title, field values, and provenance before and after, and undo or redo restores them. Items whose files are offline or missing are skipped and counted in the status bar.
- **Extra fields** (#95): every page has an **Extra fields** section, right after Details (first when the type has none), for fields the user keeps on one item, stored in `entity.extra` (names and text values) and searchable as text like the theme's text fields. Each shows its name and value, edited in place like any field (empty removes it), with × to remove it; a row of two boxes (name, value) and **Add** (or Enter) adds one. A name already used on the item, an empty name, or an empty value is refused with the reason in the status bar. Each add, change, or removal is one Edit → Undo step (`core.fields.edit_extra`, recording the whole `extra` before and after). Scans never touch `extra`, except that notes (#379, §9 *Notes*) add Extra fields marked as theirs (provenance `extra:<name>` = `note`), which scans update until the user edits or removes one. On the page (#380) they are marked "• from the note" (an edited one "• edited"); editing one sets `extra:<name>` to `user`, removing one drops its provenance and records `note_key_removal`, and the step's undo puts both back (`ExtraChange` carries the field's provenance and removal before and after). An Extra field the user added themselves has no provenance row and is never the note's.
- **Editing in place** (#93, `ui/field_editor.py`, `core/fields.py`): a field declared `editable` (the default) and the title can be edited on the page. Double-click the value (or the ✎ that appears on hover) for a text box; Enter or clicking away saves, Esc cancels. What is typed is parsed for the field's type (whole numbers and numbers may have thousands commas, dates are `YYYY-MM-DD`, dates and times `YYYY-MM-DD HH:MM` in local time, stored in UTC); empty clears an optional field; a value that doesn't parse stays in the box, outlined, with the reason. Yes/no fields are a checkbox that saves when ticked. A save runs through the DB writer (`TagService.edit_field`), sets provenance **`user`** for that field, so scans never overwrite it, refreshes the search index, and is **one step in the Edit → Undo history**, shared with tag changes ("Undo: Set Family of 'Aileron-Regular.ttf' to 'Aileron Sans'"). Undo restores both the value and its previous provenance, so an undone edit is again the scan's to update. Values you edited show a small "• edited" mark (tooltip: scans won't change it). Refused edits (an empty required field, a value of the wrong type, a field declared `editable=False`) say why in the status bar and the page shows the stored value again. Renaming an entity never renames its file. The built-in themes mark facts that come from the file (extension, folder, size, modified, dimensions, image counts, and the assets2d artist, which follows the folder) `editable=False`; a font's family and style stay editable.
  - **Role** (`Section.role(name)`, titled by the role's `label` or name): each linked file's path, root name, size, and **offline** / **missing** status; the tooltip is this machine's full path. Up to 200 are listed.
  - **Gallery** (`Section.gallery(name)`): the role's images as thumbnails, made in one worker job (`ThumbnailResolver.resource_thumbnail`). Like a file row, a picture opens with its program on double-click (or Enter), and right-click gives the same file menu (#124; galleries had no way to open a picture before movies used one). Planned (M28, §9 *Galleries*): groups for subfolders and archives, an archive's pictures listed and opened from a temporary copy.
  - **Related** (`Section.related(name)`): links to the related entities, from either side (the relationship's `label` or `reverse_label`, else the other type's plural); a link opens that entity's page.
  - **Contents** (#87): a search of the entity's contents (`within` the entity, scoped to the types the theme lets it contain), below the other sections with a splitter between them (about 40/60). It is an ordinary search page: its own filter bar, list/grid toggle (starting as a grid), sorting, double-click to open, and tag drops. Its hidden columns, layout, and card lines are remembered per container type (`contents:<type id>` in `ui_state.json`), so every artist's page looks the same. **Tagging** applies to the items selected in the contents, or to the page's own entity when none are. `Section.custom` isn't shown yet.
  - **Related sections** (#125) work the same way: each is a search of its own (`related=(name, entity)`; `search_fields` supplies each relationship's link columns as `@<name>.a` / `@<name>.b`), titled by the section (Cast, Filmography), with list/grid/tree, sorting, thumbnails, and tagging, remembered per type (`related:<type id>`). Its header has **Add…** (#260), and each item's menu **Remove from <section>** (the selection, if the item is in it; one undo step). With contents and related sections, or several related sections, the area below the sections is tabs, and tagging applies to the selection in the current tab. Without a way to embed (no window), a related section is links with an × each.
- **Opening** (#86, #107): double-click or Enter on a result (list, grid, tree, or a Search all section) opens its page, except that types with `double_click = "open_file"` open the file; the page stays reachable with Ctrl+Enter and the menu's Open page. A page is created once per entity per window and refreshed after a scan. Clicking the navigation's highlighted item (or selecting it) goes back to it, so a detail page is never a dead end before back/forward (#88).
- **Tagging** works on the page's entity: the Tags panel's checks, Enter, Ctrl+T, and New tag apply to it.
- **Breadcrumbs** (#88): above the title, the containers the entity is in, outermost first, each a link to its page (`Aurora Studio ›`). They follow `entity_contains` upward; where an entity has several containers the chain follows the first by title, so it's stable, and the line adds "(also in N others)". A cycle (bad data) or 64 levels stops the chain.
- **Drilling down** (#89): right-clicking a result (in a list, a grid card, or a Search all section) offers **Open** and **Show contents in search**, enabled for types that can contain others (`contained_types`, at any depth). It adds a grey **"Within: Aurora Studio"** chip to the current search, first in the chip row, keeping its tag filters and text; its close button (or Clear all) removes it. What is listed within a container: Search all stays grouped by type; a view keeps its own types where the container can hold them (Images within an artist lists that artist's images), and otherwise lists everything the container holds (Artists within an artist lists its assets, not nothing). A container's detail page has **Show in search** beside its contents, which opens Search all with the chip. The grid's context menu starts with the card's actions, then Card lines and sizes.
- **Back and forward** (#88): every page shown (a view, Search all, a detail page) is recorded; **Back** and **Forward** are on the toolbar and in the **Go** menu, with Alt+Left / Alt+Right (and the platform's Back/Forward keys) and the mouse's back and forward buttons anywhere in the window. Showing the page already current isn't a step; showing a new page after going back drops the forward pages; 100 steps are kept. The navigation pane highlights the current page, and nothing while a detail page is showing (it doesn't list them). The 30 most recently shown detail pages stay alive; an older one is made again when the user goes back to it.

**Tagging panel.**
- Filter box at the top: narrows the tree as you type, keeping ancestors of matches visible; matches aliases, ignoring case and accents (§7). Matches are bold (ancestors shown for context are not); a tag matched through an alias shows it, `Money (finance)`. While filtering everything is expanded; clearing the filter (or Esc) restores the folds the user had. Down moves into the tree, on the first match. The tree starts with the top level open, shows a tag's color as a swatch, and its path and aliases as a tooltip; "No tags yet." / "No tags match …" when empty. It is loaded in a worker (`ui/models/tag_tree.py`, `ui/tag_panel.py`).
- Drag one or more tags onto an item or selection. Dropping on a **selected** row tags the whole selection (rows not loaded yet are looked up in one query); dropping on any other row tags just that row. While dragging, the rows a drop would tag get a dashed amber outline, one per run of consecutive rows (overlay frames, so cell repaints can't break it up). Drops work on the list and on Search all's sections. Each drop is one undoable step (**Edit → Undo**, Ctrl+Z); the status bar says what happened ("Tagged 2 items with 'Favorites'.", or "Already tagged…" when nothing changed, which adds no undo step). Open search pages refresh afterwards, since tag filters may match differently.
- Keyboard: type to filter, arrows to move, Enter applies the highlighted tag to the selection, Shift+Enter removes it. In detail: Enter uses the tags selected in the tree, else the highlighted one, else (while filtering) the first match; from the filter box the text is then selected, so typing the next tag replaces it. Typing letters in the tree goes to the filter box; Esc in the tree goes back to it. **Ctrl+T** (Edit → Tag selection…) shows the panel and puts the cursor in its filter from anywhere in the window. The selection is the current page's selected rows (every section's, in Search all's grouped view; rows not loaded yet are looked up). With nothing selected, the status bar says so and nothing is recorded.
- Selection summary: each tag shows a tri-state check (all / some / none of the selected items). Clicking toggles between applying to all and removing from all. Only tags applied directly count (a parent shows none unless it is applied itself). Counts are computed in a worker (`core.tags.tag_counts`, batched) 150 ms after the selection settles, and again after any tagging, undo, or page switch; stale answers are dropped. Clicking a check doesn't change it directly: it requests the tagging (the same path as Enter), and the check follows once that's done. A line above the tree says how many items are selected; tooltips add "On 1 of the 3 selected items". With nothing selected there are no checks.
- **Right-click a tag**: "Show only items with 'Iceland'" / "Hide items with 'Iceland'" add it to the current search as an include or "but not" chip (Search all opens if the current page isn't a search); "Add 'Iceland' to / Remove it from the N selected items" tag the selection (disabled with nothing selected). Right-clicking one of several tags selected in the tree acts on all of them ("2 tags").
- "Create tag '…'" appears when the filter text matches nothing. It sits right under the filter (the empty tree hides), and Enter does the same. The text may be a path: `Places > Norway` (">" with spaces around it) or `Places › Norway` creates Norway under Places, creating missing parents too, all as one undo step (`split_tag_path`, `add_tag_path`, `TagService.add_path`); "/" is not a separator, so names like "AC/DC" stay whole. The button shows the path as it will be created. With items selected, the new tag is also applied to them ("…and add it to 2 items"), a second undo step. Shift+Enter never creates.

**Tag manager.** Full tree with usage counts; add, rename, reparent (drag or "Move to…"), merge, delete with subtree options, aliases, colors. Undo within the session.

- **Layout** (`ui/tag_manager.py`): a filter box and the tag tree on the left, the selected tag's details on the right (path, color, description, what it applies to (§7 *Tag types*), aliases, usage); editing arrives with #68–#70. The tree has two count columns: **Items** (tagged with the tag itself) and **With sub-tags** (distinct items tagged with it or any tag under it). Counts come from `core.tags.tag_usage`: one grouped query, then one distinct count per tag with children (about 24 ms for 300 tags over 50k items), in a worker, and are reloaded after any tagging or undo. Filtering, folds, and the selection behave as in the tagging panel.
- **Add, rename, move** (#68): **New tag…** (top level) and **New sub-tag…** (under the selected tag) ask for a name; tags are renamed in place (F2, double-click, or **Rename**); a tag moves by dragging it onto another tag (or onto empty space for the top level, or between rows for that level's parent) or with **Move to…**, a picker with a filter and a "Top level" choice in which the tag and its sub-tags are greyed out (`ui/tag_picker.py`). A move isn't confirmed first: it can be undone (Ctrl+Z), and the status bar shows the affected item count ("Moved 'Beach' under 'Topics' (2 items)."), which is how §7's "Show the affected item count" is met. Refused operations (a duplicate sibling name, a move under itself) explain themselves in the status bar.
- **Merge and delete** (#69): **Merge into…** picks the target in the same picker (the tag and its sub-tags greyed out, no top level) and says what will happen before confirming ("2 items tagged “Beach” will be tagged “Places › Iceland” instead. “Beach” becomes another name for it, and is then deleted."). **Delete…** confirms; for a tag with sub-tags it offers "Delete X and its N sub-tags" (the default) or "Delete only X; move its sub-tags up to …", and shows how many items will lose a tag for the current choice (with sub-tags: every item with any tag in the subtree; moving them up: only the tag's own items). The counts come from the page's usage figures, so the dialogs open without waiting. Both are undoable, and the status bar repeats the count afterwards.
- **Colors, descriptions, aliases** (#70) are edited in the details pane: **Choose…** (the system color picker) and **Clear** for the color; the description in a text box with **Save** and **Revert** (enabled once it differs); aliases in a short list with **Remove**, and an "Add another name…" box (Enter adds). Each change is one undoable step. Unsaved description text is kept per tag, so neither a reload (after any tag change) nor looking at another tag loses it; Revert discards it. The page's buttons (New tag…, Sub-tag…, Rename, Move…, Merge…, Delete…) are a toolbar across the page, so when it's narrow the ones that don't fit move into its overflow menu (…) instead of widening the page; the navigation pane has a minimum width so no page can squeeze it.
- **Undo / Redo** (#71): every tag operation and every tagging (drops, Enter, checks, the menus) goes on the session's one history. **Edit → Undo / Redo** (Ctrl+Z / Ctrl+Y) name the step ("Undo Merge 'Beach' into 'Iceland'"); the Tag manager's toolbar also has short **Undo** / **Redo** buttons whose tooltips name it, disabled when there is nothing to undo or redo. After an undo or redo the pages, the Tags panel, and the tag manager reload, keeping their selection when the tag still exists, and the status bar says what was undone ("Undid: …"). Steps run one at a time in the order asked, on the same one-thread pool as tagging.

**Triage.** Tabs: resources not linked to any entity; entities with no tags; entities whose linked resources are all missing. Bulk actions: link to entity/role, tag, dismiss (hide until changed).

- **Page** (#110, `ui/triage.py`, `core/triage.py`): TOOLS → **Triage**, three tabs, each with its count.
- **Unlinked files:** a table (folder, path, size, offline) of the first 10,000 files no item links; folders and missing files aren't listed. Actions: **Open file**, **Show in file manager**, **Skip in scans…** (adds an exact exclude pattern per file to its root, with `*`, `?`, `[` bracketed; the next scan flags them skipped, which takes them off the list), and **Dismiss**.
  - **Link to item…** (#243, `ui/link_dialog.py`, `core/links.py`): a dialog with a search box. It lists matching items (title and type) among the types with a role that takes every selected file, then offers those roles. Linking is one undo step, and in a one-file role the file replaces what was there.
    - The link is marked `by_user`: scans respect it (§9 ingest context), Re-read leaves the user's files out, and the file leaves the Unlinked list.
    - On the item's page the file row says "linked by you", and its menu has **Unlink from this item** (one undo step; only for links made by hand).
    - A theme may have no role for some files (the music theme's albums hold only their folder, so a stray `cover.jpg` can't be linked); the dialog says so.
  - A theme may read files without linking them (a cover image found in its folder), so some files here are expected.
- **Untagged items** and **Missing files** are ordinary search pages with `SearchSpec.triage` (`"untagged"`: no tag of its own, or none from a container with Inherit tags; `"missing"`: at least one linked file, and none that isn't missing; offline isn't missing). The Tags panel and drops tag their selection, as on any search page.
  - Untagged items has **Dismiss**.
  - Missing files has **Delete…** (after a question; the items and their tags go, never files; one undo step through the whole-entity snapshots of actions, §9) and **Show where they were** (opens the folder the first file was in, or says it's gone too).
- **Dismissing** hides until changed: `triage_dismissal(list, target_id, marker)` stores how the thing looked. A file's marker is its size and modification time; an item's is its stored `updated_at`, which edits and re-reads change. The lists leave out rows whose marker still matches. It is one undo step.
- Counts and the files table are read in a worker, and refreshed after tagging, undo, a scan, or a configuration change.

**Dedupe.** Groups of exact duplicates (fingerprint) and theme-suggested near-duplicates. Side-by-side comparison of files and entities (format, size, resolution/bitrate, tags). Actions: merge entities (§13), keep both files as versions under one entity, or mark "not a duplicate." Never deletes files.

- **Similar items** (#118): a second tab lists the theme's near-duplicate pairs (how alike, the type, both items), most alike first, with a count on the tab and a note when keys were too loose to compare. Double-click opens the first item, and the menu either one.
- **Compare pane** (#119, `core/compare.py`, `ui/compare_view.py`): the page splits, its lists on top and the compare pane below, which follows the current tab's current row; a refresh (after a scan or a tag change) keeps the same group or pair current while it's still listed. A similar pair shows its two items. An identical-files group shows the items using its copies (one column each, at most 6, saying how many more); when every copy belongs to one item it says so and shows that item, whose files row lists the copies. Each column is headed by the item's name, with its thumbnail, then a row per fact: type, name, the theme's detail fields, the user's own fields, tags, how many items it contains (containers only), and its main files (the primary role's, or every role's without one): their formats, total size, and places (at most 5, then "and N more"; folders count, so an album shows where it is). Rows whose values differ are highlighted (bold label, tinted cells); an empty value shows as a dash. Double-clicking a column (or its heading) opens the item. Its **Merge…** button merges the items shown, **Keep both as versions** does so at once, and **Not a duplicate** hides the group or pair (§13).
- **Page** (exact duplicates, #117, `ui/dedupe_view.py`): TOOLS → **Dedupe** shows a summary ("3 groups of identical files; the extra copies take 12.4 MB") over a tree of groups. Each group shows its first name and copy count, the space wasted, its size, and its check result; it expands to its copies, showing where each is, its size, its items, and same / differs. **Check** verifies the selected groups (a copy's row selects its group); it is greyed out, with a tooltip saying why, until something is selected. **Check all** verifies every group (greyed out with none). **Activity panel.** Scan progress per root, fingerprint and thumbnail queues, offline roots, ingest and thumbnail errors with the affected paths.

- **Where** (#111, `ui/activity.py`): a dock under the results, which can be moved or floated, hidden until asked for. It opens with **View → Activity** (Ctrl+Shift+A) or the status bar's problem badge ("⚠ N", shown when there are problems). It never opens by itself.

- **Thumbnails:** "Making thumbnails: N left" while the background queue runs (§6 step 7).
- **Folders:** each root's state: online, offline with the reason, not watched, or not scanned yet. It is read in a worker when the panel opens, after a scan, and after a configuration change.

  - **Show in file manager** (also double-click) for rows with a path.
  - **Copy** puts every row on the clipboard as tab-separated text.
  - **Clear** empties the log.
- **The log** (`core/activity.py`, `KeepSession.problems`): kept for the session only, the newest 1,000. It is safe from any thread, with a version counter the window checks once a second.
  - Scans add what each root's report holds: unreadable folders and files, ingest failures, the theme's warnings, and offline roots.
  - The thumbnail resolver adds files it couldn't make a picture of (`ThumbnailResolver.report`), once each per session, since failures aren't retried.
  - A scan that fails outright is added too.

## 13. Dedupe and entity merge

- **Exact duplicates:** resources with equal fingerprints (optionally verified with a full hash).
  - **Grouping** (#117, `core/dedupe.py`): files with a fingerprint, not missing or skipped, that share it with another. Each group lists its copies with the items using them. Groups come most space wasted first (size × extra copies). Offline copies are listed but can't be checked.
  - **Checking** reads a group's files whole (blake2b) only when asked, in a worker, and splits a group whose files share a fingerprint but differ in the middle. The results are *same*, *differs*, or *couldn't read* (offline, no path here, or an error).
  - Full hashes are kept for the session only (`KeepSession.verifier`), keyed by each file's id and its size and time **as they are when checked** (a quick `stat`, not the last scan's values), so a file changed even since the last scan is read again. Nothing is stored in the keep. A copy that changed since the last scan says so ("changed since the last scan; press F5"); a scan updates the groups.
- **Near-duplicates:** the theme's `similarity(a, b)` hook scores candidate pairs within a type (music: normalized artist + title + duration; images: a perceptual hash). The core only compares candidates produced by cheap blocking keys the theme supplies, never all pairs.
  - **Theme API** (#118): `Theme.blocking_keys(type, record) -> Iterable[str]` (cheap, from the record's fields; the default gives none), `Theme.similarity(type, a, b) -> float` from 0 to 1, and `Theme.near_duplicate_threshold` (default 0.9).
  - **Finding** (`core/dedupe.near_duplicates`): each type's items are read once as records and bucketed by key; pairs sharing a key are scored once each. Pairs at or above the threshold are listed, most alike first. A key shared by more than 200 items is skipped (too loose to help, and slow) and counted. A theme hook that raises is logged and skips that item or pair.
  - **music:** songs keyed by normalized artist and title. Two on the same album are different tracks (versions are already one song), so they score 0. Otherwise the score is 1 within 2 seconds of length (or with a length unknown), falling to 0 at 30 seconds apart.
  - **assets2d** (theme version 2): images get a 64-bit difference hash (`phash`, a field not shown on pages), computed when the image is read (decoded small: JPEGs with `draft`). Keys are the hash's four 16-bit quarters, so hashes within 3 bits always share one. The field also holds the picture's average color (6 more hex digits; transparent parts count as mid grey), because the difference hash sees only light and dark: two pictures whose colors are more than 40 apart (RGB distance) score 0, so a recolored icon of the same layout doesn't pair. Otherwise similarity is the share of bits that match; the threshold is 58/64 (at most 6 bits differ). Existing keeps read every file again once after the upgrade, to fill in the hash.
- **Entity merge:** the kept entity absorbs the other's tags, role links, containment edges, relationships, and `user`-provenance field values (conflicts are shown for the user to choose). The merged entity id is recorded so saved searches and history can redirect. Files are never touched.
  - **Doing it** (#120, `core/merge.py`): items of one type only. The kept item takes the others' tags, containers and contents (cycles are refused by the closure), and relationships (in a `many=False` relationship it keeps its own partner). Their files move to it as links made by hand (`by_user`), so scans never move them back; in a one-file role that the kept item already fills, the other's file is left linked to nothing and Triage lists it as unlinked. Hand-set values (fields, the title, extra fields) come along; where two items' hand-set values differ, the user picks one in the dialog (the kept item's by default). Extracted values are the kept item's own. The others are deleted and recorded in `entity_merge` (§5).
  - **Staying merged:** a scan that reads a merged item's file again doesn't recreate it, whether the theme finds items by key (`ctx.upsert`, music's songs) or through their files (`ctx.entities_of`, assets2d's pictures; §9). The kept item's values keep coming from its own files. Found testing on the assets demo: remembering keys alone let a merged picture come back.
  - **Redirects:** a page open on a merged item (or opened from history) shows the item it went into, with a note, while the merge stands (each refresh asks for the item opened, so after an undo the page is that item's own again); a saved search *within* a merged item searches within the kept one (`search.py`, one step through `entity_merge`).
  - **Undo:** one step (`MergeChange`): whole-item snapshots before and after of every item touched (the kept one, the merged ones, and their neighbours), plus the `entity_merge` rows written and repointed.
  - **Dialog** (`ui/merge_dialog.py`): the compare pane's **Merge…** (two or more items; greyed out, saying why, when their types differ) opens it. Radio buttons choose the item to keep (the left column by default; each named with its first file's place, since titles often match). The plan (`plan_merge`, in a worker, again when the kept item changes) says what it gains ("1 tag, 1 file and 2 containers"), lists conflicting hand-set values with a radio button per item, and lists files that will be left linked to nothing.
- "Keep both as versions" links the second file to the kept entity under the same primary role.
  - **Done as a merge** (#121): Merge already moves the other items' files into the kept item's roles, so a song's copies become its versions. **Keep both as versions** (or *Keep all*, for more than two) in the compare pane merges into the left item at once with the defaults (its own hand-set values win; no dialog), and is offered only when that is what happens: items of one type whose primary role holds several files (`Comparison.versions`). For one-file roles (pictures) only Merge… is offered, since a second file has nowhere to go.
- **Not a duplicate** (#121, `core/not_duplicates.py`): the compare pane's **Not a duplicate** hides the current identical-files group or similar pair from the Dedupe page (`dedupe_dismissal`, §5). A group is remembered with its files and shows again once they change (a third copy, one gone), since the user judged only the copies there were; a pair stays hidden. Each tab's summary says how many are hidden; **Show dismissed (n)**, beside the tabs, lists them greyed, where the button reads **Show as a duplicate again**. Marking and unmarking are each one undo step (`NotDuplicateChange`).
